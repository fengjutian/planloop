## 摘要

| # | 结论 | 证据 | 强度 |
|---|---|---|---|
| 1 | 在「模型自己宣布完成、但不算完成」这类失效上，**强制验收 + 带诊断的失败反馈**把成功率从 0 拉到 100% | B0 0/10、B1 0/9、B2 9/9；Fisher 单侧 `p=1.1e-5` / `2.1e-5` | 强 |
| 2 | 收益**全部来自失败反馈通道**，不来自执行器的其余部分（上下文注入、工具、提前停止） | B2C 0/6 vs B2 6/6，`p=1.1e-3`；B2C vs B0 `p=1.00` | 强 |
| 3 | 关键的不是「多给一次机会」，而是失败输出里**带不带诊断** | B2D 0/5 vs B2 6/6，`p=2.2e-3`；prompt 级证据（§4） | 强 |
| 4 | 「约定写在文档里」这类陷阱**对该模型不成立**（负结果） | 12/12 全过，B0 一次没挂 | 中 |
| 5 | 验证的**成本不是常数**，随任务形态翻转 | 短任务 0.70×、长链 1.43×、hidden 0.59× | 中 |

一句话版本：**这个项目能证明的不是「验证有用」，而是「失败反馈里的诊断信息有用」——
而且只在模型自己宣布完成的那类失效上成立。**

## 1. 实验装置

四个臂共用同一批题、同一个判据、同一个成功判定；**只有「模型被告知了什么」在变**。

| 臂 | 执行方式 | 节点验收 | 模型被告知失败？ | 失败带诊断？ | 有重试？ |
|---|---|---|---|---|---|
| **B0** | 单发 JSON 动作（盲） | 无 | 否 | — | 否 |
| **B1** | N 次盲猜取多数 | 无 | 否 | — | 否（只是重来） |
| **B2C** | planloop 执行器 | 永远通过的桩 | 否 | — | 否 |
| **B2D** | planloop 执行器 | 安静判据 | **是** | **否** | **是** |
| **B2** | planloop 执行器 | held-out 判据 | **是** | **是** | **是** |

判据不可写是这套实验的前提，用三道防线保证：

1. **工具层**：`Tools._resolve` 拒绝工作区外的路径，`read`/`write` 都抛 `ToolError`；
2. **路径不泄漏**：判据放在工作区外的临时目录，模型只能从验收命令里看到路径，看不到断言；
3. **运行后扫描**：判据首行带注释标记 `planloop-oracle:<task key>`，unittest 永不打印，
   但模型若把判据抄进工作区就会带上它——**抄了该次运行作废**。

> 第 2 条有个诚实的边界：**判据的路径与测试函数名会通过失败输出（traceback）泄漏给模型**。
> 这是真实的失败反馈（相当于 TDD 的红灯），但「模型看不见判据」只成立于「判据文件内容不可读、不可改」这一层。

## 2. 结论一：验收 + 失败反馈 = 0% → 100%

held-out 判据，28 次真实模型样本：

| 配置 | 成功 | 平均 tokens | 平均用时 |
|---|---|---|---|
| B0 单发（盲） | **0/10** | 14445 | 104s |
| B1 三次投票（盲） | **0/9** | **39576** | 283s |
| B2 验证 + 带失败信息重试 | **9/9** | **8322** | 44s |

Fisher 单侧精确检验：B2 vs B0 `p = 1.1e-5`，B2 vs B1 `p = 2.1e-5`。

三个事实同时成立：

1. **B0 会交付坏东西**——它写的实现对自己写的测试完全正确（`return a / b`、
   `sum(values) / len(values)`），但真实判据要求的是 `ValueError` 与空列表返回 0。
   没有强制验收，这就是上线的东西。
2. **B1 救不回来**——三次独立尝试都看不见那条要求，多数票仍然是错的，
   而且花了 B2 的 **4.8 倍** token，成功率是 0。**「多发几次」不能替代验收。**
3. **B2 救回来了，而且最便宜**——验收失败输出（`ValueError not raised` /
   `ZeroDivisionError: division by zero`）本身就是那条缺失的要求，带着它改一次就补上了。

**成立的前提有三个，缺一不可**（缺一条结论就不成立）：

- 模型**看不见**判据的断言（真实判据比模型自己的测试更严）；
- 失败输出**足够诊断**；
- 一次重试**够用**（补一条分支，不是重做整个功能）。

---

## 3. 结论二：拆开执行器——收益不来自执行器

B2 不是「纯验证」，是整个执行器（上下文注入 + 每步复核 + 带失败信息重试 + 提前停止）。
于是加了 **B2C**：同一个执行器、同一套工具、同样的提前停止，**只把节点验收换成永远通过的桩**。

| 配置 | 成功 | 平均 tokens | 样本 |
|---|---|---|---|
| B0 | 0/6 | 14585 | 6 |
| B2C（执行器在、验收关掉） | 0/6 | 7234 | 6 |
| B2 | **6/6** | 8360 | 6 |

B2 vs B0 / B2 vs B2C 均 `p = 1.1e-3`；**B2C vs B0 `p = 1.00`（无差别）**。

> 结论：**这批任务上的成功率收益 100% 归因于失败反馈通道，0% 归因于执行器的其余部分。**
> 执行器本身不是护身符，它只是把失败反馈送到位的那根管子。

---

## 4. 结论三：拆开「重试机会」与「诊断信息」

上一版消融把两者一起去掉了（B2C 既不反馈也不重试）。**B2D** 只拆开这两个因素：
验收是真的会失败、模型**会被告知失败**、**会得到一次重试**——只是失败输出里没有诊断。

| 臂 | 成功 | 平均 tokens | 平均执行器调用 | 样本 |
|---|---|---|---|---|
| B0 | 0/6 | 12484 | 8.67（模型调用） | 6 |
| B2C | 0/6 | 7121 | 1.00 | 6 |
| **B2D** | **0/5** | 14809 | 2.00 | 5 |
| **B2** | **6/6** | 8973 | 1.00 | 6 |

Fisher 单侧：B2 vs B2D `p = 2.2e-3`；**B2D vs B2C `p = 1.00`**、B2D vs B0 `p = 1.00`。
另两次独立复现格局完全相同（0/6、0/6、0/6、6/6）。

**B2D ≈ B2C**：多给一次机会、但不给诊断，等于没给。

### 4.1 prompt 级证据：模型到底看见了什么

只看成功率说不清 B2D 为什么是 0/5——两种解释必须先分掉：
「安静判据让重试根本没触发」还是「重试触发了但没有诊断」。
方法是把模型实际收到的 prompt 抓下来（真模型，spy 记录每次 `complete(prompt)`）：

| 臂 | 任务 | 结果 | 节点执行 | 模型调用 | **带 traceback 的 prompt** |
|---|---|---|---|---|---|
| B2D | mean_empty_hidden | 失败 | 2（重试了） | 16 | **0 / 16** |
| B2 | divide_zero_hidden | 成功 | 1 | 8 | **7 / 8** |
| B2 | mean_empty_hidden | 成功 | 1 | 8 | **7 / 8** |

三件事一次说清：

1. **B2D 的重试确实发生了**（节点执行 2 次，第二次带 supervisor 纠正），
   但 16 次调用里模型一次也没看到过 `ZeroDivisionError` / `FAILED (...)`，
   只看到 `exit=1 (want 0)` 和 `ACCEPTANCE FAILED: ...`。
2. **B2 的成功不是「模型一次就写对」**——8 次调用里 7 次带着真实 traceback，
   模型是**看着报错改对**的。
3. **「节点执行 = 1」不矛盾**：纠错发生在**同一次节点执行内**
   （执行器每步都做 L1 检查，失败输出直接进下一轮 prompt），根本没用上 scheduler 的重试。

所以因果链是：**失败输出带诊断 → 模型在同一次执行里改对 → 成功**；
少了诊断这一环，重试多少次都一样。

## 5. 负结果与不适用的场景

诚实的负结果和"不适用"和正面结论一样重要：

| 现象 | 数据 | 含义 |
|---|---|---|
| 约定写在 `calc/README.md` | `division_convention` B0 **4/4 全过** | 模型把 README 里的约定读进去了 |
| 可见测试指向归档副本 | `legacy_copy` B0 **4/4 全过** | 两份拷贝都改了 |
| 长链改名任务（3~8 个调用点） | B0 **16/16**、B2 **16/16** | 这类失效对模型不成立，测不出差别 |
| 采样噪声 | 温度 1.0 下 B0 **12/12 全过** | 失败不是采样噪声造成的 |
| B1 投票逻辑自检 | `p_correct=1.0` 必过、`p_correct=0.0` 必挂（单测） | 投票实现不会把对的答案投成错的，盲投票基线没有被测错 |

**结论：能被拦住的只有「约定本身不可见、只有判据知道」的那一类失效。**
文档约定、代码考古这类真实工程手段，对一个会读文档的模型不起作用——
它们不是「无效做法」，只是**测不出差别**，不能拿来当失败源。

## 6. 成本：不是常数

「验证要花多少钱」没有单一答案，实测三个任务族是三个数：

| 任务族 | 场景 | B0 | B2 | B2 / B0 |
|---|---|---|---|---|
| 短任务（5 题 × 2 模型） | 模型一次就对 | ~3800 | ~2650 | **0.70×**（更省） |
| 长链任务 | 模型一次就对 | 14837 | 21176 | **1.43×**（更贵） |
| hidden 判据 | 模型本来就会错 | 14021 | 8321 | **0.59×**（更省） |

- 模型一次就对、任务短 → 上下文注入 + 提前停止让 B2 **更便宜**；
- 模型一次就对、任务长链 → 每步重发整个仓库，B2 **贵 43%**；
- 模型本来就会错 → 一次失败 + 一次带诊断的重试，比盲写一遍**更省**。

**验证的价值只在该出错的场景里显现。**

## 7. 这份报告不证明什么（效度威胁）

1. **任务集窄**：全部核心结论来自 2 道「模型自己宣布完成」的题 + 1 个任务族。
   roadmap 的验收门是 **≥10 个真实任务**，现在差得远。
2. **单模型**：只有 MiniMax-M3.1-Flash。结论是否跨模型成立未测。
3. **样本量小**：每格 3~5 次。Fisher 检验只说明「在这个样本上差异不是偶然」，
   不构成普遍结论；`B2D 0/5` 的 p 值对 1 格被剔除很敏感。
4. **判据泄漏**：traceback 会把 held-out 测试的**函数名**露给模型。
   这是真实反馈，但也意味着模型知道了验收长什么样。
5. **策略会中断运行**：实测有 1/24 的格子因模型写了嵌套 shell（`$(`/反引号）
   触发确认规则、需要人工批准而**整轮被拦下**——这类格子没有测到验收行为，必须剔除。
   剔除与否会直接改变 B2D 的分母。
6. **B2 内部机制未完全拆开**：B2 = 上下文注入 + 每步 L1 复核 + 带诊断反馈 + 提前停止。
   本轮拆掉了「验收/反馈/重试」，**没有**单独拆「提前停止」与「每步复核」的贡献。

## 8. 仪表自身的缺陷（本轮修掉的三个）

它们都不会让程序报错，**只会悄悄把结论推向有利于假设的方向**——这比模型出错更危险。

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 17.1 | 合并脚本里 `contaminated` 吃 dataclass 默认值 `False` | 报告里「24/24 未发现副本」**根本没测过**，是默认值渲染出来的 | 从日志行的 `CONTAMINATED` 标记读，缺字段报错 |
| 17.2 | `attempts` 取自 `getattr(model, "attempts", 1)`，真实模型没这个属性 | 「重试次数」这一列**恒为 1**，而 B2D 的结论恰恰取决于它 | 改从 scheduler 的 `result.outcomes` 取（与模型实现无关） |
| 17.3 | `max(1, len(outcomes))` 把「跑了但失败」和「根本没跑完」压成同一个数 | 被策略中断的格子被算成一次失败，**凭空给消融假设加了一票** | `Outcome` 增加 `status`/`blocked`，按原因分类，中断的格子单列剔除 |

> 教训：benchmark 不只是用来测模型的——**它自己会把 harness 的 bug 逼出来**。
> 如果只看「成功率」这一个数字，那次让整轮长任务死掉的 `ToolError` 崩溃
> 会被当成「实验失败」而丢掉，而不是变成一个产品 bug 的报告。

## 9. 复现

```bash
# 全量单测（195 项，约 60 秒）
python -m unittest discover -s tests -t . -q

# 离线冒烟：题目有效性 + 度量管线（不烧 API）
python -m planloop bench --reps 2 --p-correct 0.5 --seed 3 --tasks divide_zero_hidden,mean_empty_hidden

# held-out 判据对照（真实模型）
python -m planloop bench --real --model MiniMax-M3.1-Flash --reps 3 \
    --configs B0,B1,B2 --tasks divide_zero_hidden,mean_empty_hidden --out docs/bench-hidden.md

# 四臂消融（带状态记录）
python -m planloop bench --real --model MiniMax-M3.1-Flash --reps 3 \
    --configs B0,B2C,B2D,B2 --tasks divide_zero_hidden,mean_empty_hidden --out .demo/ablation.md

# 采样噪声轴
python -m planloop bench --real --model MiniMax-M3.1-Flash --temperature 1.0 --reps 2 --configs B0

# 产品本体（四组对照，约 20 秒）
python -m planloop demo --dir .demo
```

## 10. 下一阶段

按 `docs/roadmap.md` 的验收门「至少 10 个真实任务、每种配置重复运行、
报告可复现且成功结论完全由独立 oracle 给出」，还差三件事：

1. **补任务集**（最关键）：把 2 道合成题扩到 ≥10 道真实任务，
   覆盖更多失效形态（跨模块契约、性能、并发、依赖升级…）。
   每道题都要有**双向自检**（correct 分支必过、wrong 分支必挂）——
   题目本身是坏的，benchmark 会给出与事实相反的结论。
2. **换模型复现**：至少再加一个模型，检验「诊断有用」是否跨模型成立。
3. **补上 B2 内部的剩余混淆**：单独拆「每步 L1 复核」与「提前停止」，
   以及把 B0 的上下文预算对齐（早期版本 B0 只有 B2 一半）。

同时建议把 §7.5 那类「被策略中断的格子」做成常态统计项——
真实模型会写嵌套 shell，这在别的项目里也会发生。
