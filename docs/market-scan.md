# 市面方案调研与设计修订

> 调研时间：2026-11。目的不是"看看别人怎么做"，而是**判断我们哪些工作是在重复造轮子、哪些押注是别人没做的**。
> 注：这一领域的评测数字大多是厂商自测，口径互相打架（Mem0 报 LOCOMO 提升，Zep 公开质疑其口径），所以下文只引用机制，不引用效果数字。

## 一、四类现有方案

| 类别 | 代表 | 核心机制 | 对我们的意义 |
|---|---|---|---|
| 项目文件式记忆 | [CLAUDE.md](https://code.claude.com/docs/en/memory)、[AGENTS.md](https://www.infoq.com/news/2025/08/agents-md/) | 人写、随仓库提交、启动整篇注入 | 我们的 `fact` 表 = 可查询版 AGENTS.md，但**没人保证它仍然为真** |
| 记忆基础设施 | [Mem0](https://raw.githubusercontent.com/lhl/agentic-memory/a26d9df2e1f93cfc0a80900ccd98d25b681bef27/references/chhikara-mem0.md)、[Zep/Graphiti](https://huggingface.co/datasets/quantellence/srb-data/blob/main/datasets/public_ai_memory/papers/09_graphiti.md)、Letta | 提取 → 判重 → 增删改；向量或时序图 | 我们把"提取"换成了"证据验证" |
| 自我反思式 | Reflexion、ExpeL、Voyager | 失败 → 写反思文本 → 下次检索 | 我们的 `lesson` 是它的**可执行版**（带护栏） |
| 上下文管理 | Claude Code compaction、[CTXAgent](https://export.arxiv.org/pdf/2610.34425) | 摘要压缩、子 agent 隔离、按需重读 | `blackboard` 切片是同一思路的更硬版本 |

## 二、市场共识（不必自造的）

1. **分层**：global / project / session。对应我们的 `scope`。
2. **写决策**：Mem0 的 ADD / UPDATE / DELETE / NOOP。我们原来只有 `upsert` 覆盖，**丢掉了"为什么改"**。
3. **时间维度**：Zep 的双时态（事件时间 vs 记录时间）比 TTL 精确——事实不是"过期"，是"在某段时间内有效"。
4. **混合检索**：BM25 + 向量加权。已是标配，不是优势。
5. **记忆中毒是真实威胁**：[MemPoison](https://neurips.cc/virtual/2026/loc/sydney/poster/139557) 一类工作证明一条被注入的记忆可以长期污染后续任务。这反过来支持我们的证据 + 信任衰减设计。

## 三、市场空白（我们的押注，也是风险）

| 空白 | 现状 | 我们的做法 | 风险 |
|---|---|---|---|
| 记忆可验证 | 产品都接受"模型提取的事实"，入库前不验证 | 护栏/证据必须现场跑通 | 没有现成经验可抄 |
| 负向记忆可执行 | Reflexion 只存反思文本 | lesson 带验收项，模型不听也拦得住 | 触发条件写不好会误伤 |
| 进度 = 缺口清单 | 产品做 todo list / 百分比 | 从日志生成缺口、stub、覆盖率 | 未经验证 |
| 文档-代码一致 | 基本没有标准，最多 doctest | 声明即断言 | 工程琐碎 |

四个里，**前两个是真赌注**，后两个是"做了更好"。

## 四、据此修订的五处设计

| # | 修订 | 理由 | 状态 |
|---|---|---|---|
| 1 | 写决策改为 ADD / UPDATE / DELETE / NOOP + 变更历史 | 覆盖式 upsert 让"为什么改变"不可追溯 | ✅ 本次实现 |
| 2 | TTL → 双时态 `valid_from / valid_to` | 过期不是删除，是一段有效区间的结束 | ✅ 本次实现 |
| 3 | procedure 可执行化（`exec_spec`） | 文字流程记不住也用不上，命令才能复用 | ✅ 本次实现 |
| 4 | `public.db` 导出为 AGENTS.md | 互操作：别的工具不认识 SQLite，认识 AGENTS.md | ✅ 本次实现 |
| 5 | 度量"第二次同类任务快多少" | 没有这个，前四项都是猜 | ⏳ 待做 |

## 五、明确不跟

| 不跟 | 原因 |
|---|---|
| 全量图数据库 | 单仓库规模用 SQLite 足够，图查询的复杂度换不来收益 |
| 托管记忆服务 | 价值在"验证"不在"存储"，用别人的存储丢掉控制权 |
| 语义检索军备竞赛 | 检索是商品，验证才是差异 |
| 自研 embedding | 有接口就用，没有就用哈希 |

## 六、对既有判断的修正

1. "语义检索不可解释，所以只用 key + BM25" —— **过窄**。主流是混合检索，纯词法在自然语言查询下召回不足。保留混合，但要说明默认 embedder 是哈希、不是语义。
2. "记忆最容易崩在膨胀" —— 市场数据支持：所有产品都在做摘要、压缩、淘汰，没有一个靠"记得更多"赢。注入预算（500 字符）保持。

## 七、重排后的优先级

```
1. 写决策 + 变更历史        ← 审计与记忆的交汇点
2. 双时态                   ← 让"过期"可解释
3. procedure 可执行化       ← 唯一能真正省步数的
4. public.db → AGENTS.md    ← 互操作，几乎零成本
5. 度量第二次是否更快        ← 没有它，前四项都是猜
```

P0（运行持久化与续跑）仍排在所有记忆工作之前：记忆再好，进程一退就全丢。
