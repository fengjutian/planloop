# 已知失效模式

这份文档存在的意义：**先把"什么时候会害你"写清楚**，比事后解释便宜得多。

## 一、结构性限制

### 1. 没有 git 提交点

**现状**：模型可以连续改几十个文件，没有任何回退点。
**后果**：长任务一旦走错方向，只能人工 `git checkout`，且不知道"从哪一步开始错的"。
**缓解**：见 `docs/audit-rollback.md`。在实现之前，不要用它跑超过 10 步的任务。

### 2. 运行状态不持久

**现状**：`Plan`、节点状态只在进程内，进程退出即丢失。
**后果**：中断 = 从头再来。
**缓解**：计划落盘 + `--resume`（见路线图 P0）。

### 3. 上下文切片会丢信息

**现状**：每个节点只看得到直接依赖的产物摘要。
**后果**：T2 发现的坑，T3 不知道（除非写进 facts）。
**缓解**：`blackboard.add_fact()` / `add_dead_end()`，但**依赖执行者主动写，现实中它常常不写**。已知缺陷。

> **优先级下调（2026-11 实测）**：在当前任务族上，上下文注入对成功率**贡献为 0**——
> 去掉上下文注入与每步复核的执行器（B2C）与盲发（B0）无差别（`p=1.00`）。
> 所以它不是当前瓶颈；只有"跨节点依赖失效"这类任务才需要验证它。本轮**未测**那一类，不能据此说它不重要。

### 4. 串行执行

**现状**：就绪队列一次只跑一个节点。
**后果**：宽 DAG 被压成串行链，`pⁿ` 的误差复利没有任何缓解。
**缓解**：并行调度（需要先解决同文件写冲突）。

## 二、验证的边界

### 5. L2 评委不可靠

模型评审只能判断"看起来对不对"，且同一模型家族会互相认可。
**现状缓解**：强制引用原文，引用不到即失败；证据不存在即失败。
**残余风险**：C 级证据不应该支撑"任务完成"的结论，报告里必须标注。

### 6. 验证器召回率决定一切

如果验证器只能抓 50% 的错误，10 步端到端成功率只能从 0.35 提到 0.6。
**这个数字是天花板，不是调参能解决的。**

> **补充修正（2026-11 实测）**：这个天花板至少要**拆成两段**，只盯"召回率"会漏掉一半：
>
> 1. **能不能发现失败** —— 判据抓不抓得到；
> 2. **发现之后能不能把诊断送到模型** —— 失败输出里带不带诊断。
>
> 实测证据：B2D 臂**召回了失败**（模型被告知"验收未通过"）**也拿到了重试**，
> 但失败输出里没有 traceback → 成功率 0/5；B2 只多了 traceback → 6/6（`p=2.2e-3`）。
> 也就是说：**"知道了失败"不等于"能改对"**，召回率只管第一段。
> 我们已经把第一段的召回率**测过一次**：故障注入集 3 个案例 × 33 个已知缺陷，
> 强判据（仓外 oracle）33/33、弱判据（模型自己写的测试）13/33、0 过杀
> （[判据召回率](fault-recall.md)）。
> 但那是**相对于我们自己定义的缺陷分类**——真实任务上的召回率**仍然没测**。
> 下一轮必须把真实任务拆成「正确版 + 注入缺陷版」两版，才能得到可用于真实决策的那个数。

### 7. 护栏可能误杀

一条错误的 guard 会在正确的工作上反复报警。人一旦开始无视它，机制失效。
**现状缓解**：入库前实测通过 + 误杀降权 + trust<0.2 自动报废。

## 三、记忆的边界

### 8. 跨项目污染

单文件存储不分项目作用域，"必须用 `python -m pytest`"会被带进 Rust 项目。
**建议**：按仓库隔离，全局只放与语言/工具无关的流程教训。

### 9. 无限增长

没有 TTL 与容量上限，lesson 越多误匹配越多、匹配越慢。

### 10. 只记得住"有报错"的错误

需求理解错误、设计方向错误、遗漏步骤——这些没有报错文本，签名机制帮不上忙。

### 11. 记忆的价值只在机制层面被测过——而且真实模型上这条路一开始是**死的**

**现状（脚本模型）**：已建装置（`python -m planloop membench --real`，
[记忆值不值](memory-value.md) / [脚本版](memory-value-scripted.md)）：
第二次同类任务里，教训+护栏省 1 步并拦住回归；已验证事实路径**同样**省 1 步——两条路径**收益重合**。

**现状（真实模型，2026-11-11）**：第一次换成真实模型，第一件事不是"记忆有没有用"，
而是**发现记忆这条路上有八处一测就死的环节**（详见 [bench.md](bench.md) §十九）：

1. 教训生成给模型的 500 token 预算被推理模型的思考吃光（499 reasoning token、0 输出），
   每一条教训都静默退化成兜底模板——没有原因、没有做法、没有护栏；
2. 触发条件里只要带 `error_patterns` 或 `commands`，**永远检索不到**
   （执行期上下文没有错误文本也没有命令历史，而各段是 AND 关系，一票否决）；
   实测教训出现在 **0/12** 个 prompt 里；
3. 模型写的护栏 `must` 不是机器可读格式时，判据**恒为真**——一个永远通过的保护。

三处都不报错、不崩，只是把"记忆"变成只写不读的一本账。脚本模型一个都测不出来：
脚本模型不思考，触发条件也是我们手写的。

**修好之后又发现第六处（2026-11-11，`fee` 族试点）**：推理模型有时**只交思考过程、不交答案**
（`content` 为空，客户端退回 reasoning 通道，于是回复是一段散文，
开头是 "We need answer JSON only. Need infer lesson..."，里面**一个 `{` 都没有**）。
JSON 解析失败 → 教训静默退化成兜底模板 → `source` 变成 `heuristic`，
**而且这条教训的触发条件只有 `error_patterns`，于是它在第二道任务里一次也没被检索到**
（实测教训出现在 **0/13** 个 prompt 里）。
修法：模型适配层把"只有 reasoning"标出来（`Completion.reasoning_only`），
教训生成**再试一次**并附上"只回 JSON"的严格要求；报告里新增一行
**「模型自己写的教训 X/Y 条」**，让退化**看得见**。

**第七处更阴（2026-11-11）**：教训生成器拿到的"修复"只有一行摘要
（`wrote 239 chars to shop/helpers.py`）——**没有文件内容**。
于是模型**编了一个原因**：它写下的教训说"每个档位都用 `1 - p/100`"，
而它真正写进文件的是**带档位表**的那一版。
这条编错的教训触发条件还是 `files`/`goals`（会命中下一个任务），
于是它会**带着一个错误的"做法"**灌给模型。
修法：调度器把**改过之后的文件内容**一起交给教训生成器
（`scheduler.py::_fix_excerpt`），提示词里写明"`fix` 必须描述文件里实际是什么"。
⇒ **教训的保真度是一个真实风险**，而**已验证事实没有这个风险**——
事实是把外部观测**抄下来**，教训是模型对观测的**转述**。

**第八处（隐患级，2026-11-11）**：执行器每步都记录验收失败，
但 prompt 只带**最后两条** observation——模型自己的两个动作就能把"为什么失败"顶出窗口。
修法：失败文本单独钉住，验收没过就一直显示（`blackboard.record_rejection`）。
（要说清楚：这条**不是**某次"重复读同一文件 23 次"循环的原因——
那次失败文本还在窗口里，循环是模型卡在"记忆说的"和"文件写的"之间反复对账。）

**后果**：在修好这几处之前，"记忆有效"这个结论**只在脚本模型上成立**；
真实模型上它连"被读到"都做不到。修好之后"两条路径收益重合"的结论才第一次有了真实模型的数据，
但它只在"模型一次就做对"的任务族上成立。

**而且即使装置改成"记忆有机会省事"，它也没省下来**（2026-11-11 第二轮，`contract` 族 8 reps）：
把约定藏到 prompt 之外、让"读那个文件"成为必要动作之后，
**三臂的第一步仍然都是 `read shop/helpers.py`**——事实里已经写清了函数名、文件、
契约和旧行为，模型**还是要打开源文件核对**。

⇒ **对会读代码的模型，记忆替代不了读代码，只能替代"试错"。**
记忆系统的价值必须按这个边界来设计：要省的那部分，得是**只有试错才能得到**的知识。

**但连这条结论都得打折**（2026-11-11 第三轮）：把行为从事件流回读之后才发现，
**那一族的契约是猜得出来的**——可见测试钉住 `total([100,200],10) == 270`，
模型推出 `pct(10) == 0.9` 就顺手推出 `pct(20) == 0.8`，
于是那次核对是**自愿的**（不核对也能过），记忆压根没有东西可省。
**所以"没测到收益"这句话，有一半是装置自己的毛病**（[bench.md](bench.md) §二十一）。
新的任务族 `fee`（平台费按档位取值，`pct(10)==0.88` 推不出 `pct(20)==0.75`）
把知识变成**必需**的，重新测。

**测出来的结论，以及它带来的新边界**（`fee` 族，8 次重复、有效 5 次）：
**已验证事实让模型少查 41% 的表、少花 45% 的 tokens**——
这是第一次在真实模型上测到记忆的成本收益。
但**事实臂的 2 次"红"和对照臂的 1 次"红"是同一类**：
节点的验收过了、仓外最终判据判红（模型把 `member_pct=0` 那个情况写坏了）。
⇒ **省下来的那次核对，正好是它没发现回归的那次核对。**
⇒ 所以新的失效模式是：**记忆会把"发现错误"的能力一起省掉。**
记忆系统的价值不能只按"省了多少步"算，
**要按"省掉的动作里有没有发现错误的那部分"算**——
这直接指向"要不要给事实臂也配一条护栏"。

**这一轮还暴露了两个装置缺口（已知，未修）**：
①**安全闸门会悄悄抽掉一个臂的处理**：模型用了带 `;` 的子 shell 命令 →
需要人工批准 → 基准里没人批准 → 第一道任务被拦下 → **那一轮没有教训可注入**；
而事实臂不受影响（事实是程序按"全量测试通过"存的）。
②**模型调用失败会被算成任务失败**：8 次重复里 3 次死于 provider 报错
（0 tokens、2 次调用、仓库没被碰过）。
两者都会让"臂之间"出现假的差异，**必须先修再采信结论**。

**缓解**：新增记忆能力必须在这套装置上**不劣于**基线；
真实模型的数字必须同时报**注入命中率**（`带教训的 prompt` / `带事实的 prompt` 两列）
和**到验收通过的步数/tokens**（总步数会被模型做完之后的反复确认顶满，不是成本口径）；
还必须报**行为**（从事件流回读"模型有没有去查那个隐藏约定"）——
**结果没差、行为也没差，才能说"这类任务上记忆没有可测收益"**；
否则测的还是"库里有东西"，不是"东西被用上了"。

## 四、成本与预算

### 12. token 估计是估算

脚本模型按 `字符数 / 3.2` 估算，真实 API 才返回准确 usage。
**后果**：离线实验里的"成本"是相对值，不能当账单。

### 13. 预算只在总量上硬

阶段配额是软借用（记录但不阻断），所以"规划阶段烧掉 30%"会悄悄发生。

## 五、不适用的场景

| 场景 | 为什么不适合 |
|---|---|
| 单步任务（改一个变量） | 分解与调度只增加延迟和漂移 |
| 无客观验收的创作类任务 | 只能靠 L2/C 级证据，"成功"无法证实 |
| 完全无人值守的长任务 | 第 20 步的方向性错误没人纠正 |
| 需要实时响应的交互 | 每节点多轮 ReAct，延迟不可接受 |

## 六、假设清单

实验与结论建立在这些假设上，换环境需要重新验证：

1. 任务可重复执行（仓库可重置），否则无法统计。
2. 失败有可读的错误文本，否则签名机制失效。
3. 验证命令是廉价且确定的（秒级测试）。
4. 模型稳定：同一 prompt 的行为方差不会主导结果。
5. 演示里的"模型"是脚本化的——**它证明的是机制正确，不是模型能力**。
