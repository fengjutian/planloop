# 已知失效模式

这份文档存在的意义：**先把"什么时候会害你"写清楚**，比事后解释便宜得多。

## 一、结构性限制

### 1. 没有 git 提交点

**现状**：模型可以连续改几十个文件，没有任何回退点。
**后果**：长任务一旦走错方向，只能人工 `git checkout`，且不知道"从哪一步开始错的"。
**缓解**：见 `docs/audit-rollback.md`。在实现之前，不要用它跑超过 10 步的任务。

### 2. 运行状态不持久

**现状**：`Plan`、节点状态只在进程内，进程退出即丢失。
**后果**：中断 = 从头再来。
**缓解**：计划落盘 + `--resume`（见路线图 P0）。

### 3. 上下文切片会丢信息

**现状**：每个节点只看得到直接依赖的产物摘要。
**后果**：T2 发现的坑，T3 不知道（除非写进 facts）。
**缓解**：`blackboard.add_fact()` / `add_dead_end()`，但**依赖执行者主动写，现实中它常常不写**。已知缺陷。

> **优先级下调（2026-11 实测）**：在当前任务族上，上下文注入对成功率**贡献为 0**——
> 去掉上下文注入与每步复核的执行器（B2C）与盲发（B0）无差别（`p=1.00`）。
> 所以它不是当前瓶颈；只有"跨节点依赖失效"这类任务才需要验证它。本轮**未测**那一类，不能据此说它不重要。

### 4. 串行执行

**现状**：就绪队列一次只跑一个节点。
**后果**：宽 DAG 被压成串行链，`pⁿ` 的误差复利没有任何缓解。
**缓解**：并行调度（需要先解决同文件写冲突）。

## 二、验证的边界

### 5. L2 评委不可靠

模型评审只能判断"看起来对不对"，且同一模型家族会互相认可。
**现状缓解**：强制引用原文，引用不到即失败；证据不存在即失败。
**残余风险**：C 级证据不应该支撑"任务完成"的结论，报告里必须标注。

### 6. 验证器召回率决定一切

如果验证器只能抓 50% 的错误，10 步端到端成功率只能从 0.35 提到 0.6。
**这个数字是天花板，不是调参能解决的。**

> **补充修正（2026-11 实测）**：这个天花板至少要**拆成两段**，只盯"召回率"会漏掉一半：
>
> 1. **能不能发现失败** —— 判据抓不抓得到；
> 2. **发现之后能不能把诊断送到模型** —— 失败输出里带不带诊断。
>
> 实测证据：B2D 臂**召回了失败**（模型被告知"验收未通过"）**也拿到了重试**，
> 但失败输出里没有 traceback → 成功率 0/5；B2 只多了 traceback → 6/6（`p=2.2e-3`）。
> 也就是说：**"知道了失败"不等于"能改对"**，召回率只管第一段。
> 我们已经把第一段的召回率**测过一次**：故障注入集 3 个案例 × 33 个已知缺陷，
> 强判据（仓外 oracle）33/33、弱判据（模型自己写的测试）13/33、0 过杀
> （[判据召回率](fault-recall.md)）。
> 但那是**相对于我们自己定义的缺陷分类**——真实任务上的召回率**仍然没测**。
> 下一轮必须把真实任务拆成「正确版 + 注入缺陷版」两版，才能得到可用于真实决策的那个数。

### 7. 护栏可能误杀

一条错误的 guard 会在正确的工作上反复报警。人一旦开始无视它，机制失效。
**现状缓解**：入库前实测通过 + 误杀降权 + trust<0.2 自动报废。

## 三、记忆的边界

### 8. 跨项目污染

单文件存储不分项目作用域，"必须用 `python -m pytest`"会被带进 Rust 项目。
**建议**：按仓库隔离，全局只放与语言/工具无关的流程教训。

### 9. 无限增长

没有 TTL 与容量上限，lesson 越多误匹配越多、匹配越慢。

### 10. 只记得住"有报错"的错误

需求理解错误、设计方向错误、遗漏步骤——这些没有报错文本，签名机制帮不上忙。

### 11. 记忆的价值只在机制层面被测过——而且真实模型上这条路一开始是**死的**

**现状（脚本模型）**：已建装置（`python -m planloop membench --real`，
[记忆值不值](memory-value.md) / [脚本版](memory-value-scripted.md)）：
第二次同类任务里，教训+护栏省 1 步并拦住回归；已验证事实路径**同样**省 1 步——两条路径**收益重合**。

**现状（真实模型，2026-11-11）**：第一次换成真实模型，第一件事不是"记忆有没有用"，
而是**发现记忆这条路上有十四处一测就死的环节**（详见 [bench.md](bench.md) §十九）：

1. 教训生成给模型的 500 token 预算被推理模型的思考吃光（499 reasoning token、0 输出），
   每一条教训都静默退化成兜底模板——没有原因、没有做法、没有护栏；
2. 触发条件里只要带 `error_patterns` 或 `commands`，**永远检索不到**
   （执行期上下文没有错误文本也没有命令历史，而各段是 AND 关系，一票否决）；
   实测教训出现在 **0/12** 个 prompt 里；
3. 模型写的护栏 `must` 不是机器可读格式时，判据**恒为真**——一个永远通过的保护；
4. 模型写的正则有未闭合分组 → 检索链路直接抛 `re.error`；
5. 模型把 `goals` 写成**字符串** → 按列表逐字符迭代 → 触发条件变成通配。

这几处都不报错、不崩，只是把"记忆"变成只写不读的一本账。脚本模型一个都测不出来：
脚本模型不思考，触发条件也是我们手写的。

**修好之后又发现第六处（2026-11-11，`fee` 族试点）**：推理模型有时**只交思考过程、不交答案**
（`content` 为空，客户端退回 reasoning 通道，于是回复是一段散文，
开头是 "We need answer JSON only. Need infer lesson..."，里面**一个 `{` 都没有**）。
JSON 解析失败 → 教训静默退化成兜底模板 → `source` 变成 `heuristic`，
**而且这条教训的触发条件只有 `error_patterns`，于是它在第二道任务里一次也没被检索到**
（实测教训出现在 **0/13** 个 prompt 里）。
修法：模型适配层把"只有 reasoning"标出来（`Completion.reasoning_only`），
教训生成**再试一次**并附上"只回 JSON"的严格要求；报告里新增一行
**「模型自己写的教训 X/Y 条」**，让退化**看得见**。

**第七处更阴（2026-11-11）**：教训生成器拿到的"修复"只有一行摘要
（`wrote 239 chars to shop/helpers.py`）——**没有文件内容**。
于是模型**编了一个原因**：它写下的教训说"每个档位都用 `1 - p/100`"，
而它真正写进文件的是**带档位表**的那一版。
这条编错的教训触发条件还是 `files`/`goals`（会命中下一个任务），
于是它会**带着一个错误的"做法"**灌给模型。
修法：调度器把**改过之后的文件内容**一起交给教训生成器
（`scheduler.py::_fix_excerpt`），提示词里写明"`fix` 必须描述文件里实际是什么"。
⇒ **教训的保真度是一个真实风险**，而**已验证事实没有这个风险**——
事实是把外部观测**抄下来**，教训是模型对观测的**转述**。

**第八处（隐患级，2026-11-11）**：执行器每步都记录验收失败，
但 prompt 只带**最后两条** observation——模型自己的两个动作就能把"为什么失败"顶出窗口。
修法：失败文本单独钉住，验收没过就一直显示（`blackboard.record_rejection`）。
（要说清楚：这条**不是**某次"重复读同一文件 23 次"循环的原因——
那次失败文本还在窗口里，循环是模型卡在"记忆说的"和"文件写的"之间反复对账。）

**第九处（2026-11-11，`fee` 族跑完后回读事件流才发现）**：模型写的文件触发条件
`shop/**/*.py` **永远匹配不上**——匹配用的是 `fnmatch`，而 `fnmatch` 没有 `**` 语义
（它把 `*` 换成 `.*`，但把 `/` 保留成字面量），于是这个模式要求 `shop/` 和文件名之间
**还得有一层目录**。工作区里没有子目录，所以那条教训**一次都没被检索到**。
⇒ 教训臂在 5 次配对重复里**只在 2 次真的带着教训跑**，
所以"模型写的教训有没有收益"这轮**证明不了**。
修法：文件 glob 改成按路径段匹配，`**` 表示"零段或多段"
（`memory.py::_match_glob`）；守卫测试 `tests/test_memory.py::DoubleStarGlobTest`。
⇒ **教训注入率必须和效果一起报**，不能只报效果——
注入率低的时候，"没差异"分不清是"记忆没用"还是"记忆根本没进去"。

**第十处（2026-11-11，报告生成器）**：报告在**部分数据**上除零
（首个 rep 的对照臂没有 tokens ⇒ `/(c_tok)` 抛 `DivisionError`），
**整轮已经付费的实验被带走**（[bench.md](bench.md) §十九.10，已修）。

**第十一处（2026-11-11，判据自己的路径）**：仓外判据被拼成一条命令，
`-s` 用的是**相对路径**，而命令是在工作区里跑的 ⇒ 判据永远找不到自己的目录
（`ImportError: Start directory is not importable`）⇒
**第一道任务永远不通过 ⇒ 教训压根不会产生** ⇒ 教训臂测的还是空气。
那一轮（`.membench-fee11`）在 rep 1 就止损作废。
同一份代码换个调用方式（`--dir` 传绝对路径）就正常——**装置不可复现**本身就是信号。

**第十二处（2026-11-11，判据根本没被藏住）**：判据只是"在仓外"，
但工作区锁只管 `read`/`write`，**`run` 走 shell**——模型用
`cd /d ... && type ...\oracle\r1_oracle_1.py` 读到了判据源码，
而源码里写的就是**答案**（`pct(10)==0.88`、`total(...)==198.0`）。
回读 `fee` 族 8 次重复的事件流，这类动作有 **3 次**（rep 1、rep 4、rep 5 的对照臂）。
**还有第二条通道**：验收失败文本喂回模型时，unittest 的 traceback 会打印失败的那一行源码
——那一行正是写着答案的那行（实测反馈里出现了 `198.0`）。
⇒ 那几轮的数字**作废**：测到的是"模型翻文件的本事"，不是记忆。
修法：判据**不再落盘**（喂给 `python -`，标准输入），从 stdin 来的程序
traceback 里**没有源码行**（反馈通道自动堵死）；判据的"在查什么"用**不含数字**的
描述告诉模型（否则模型只拿到一个裸 `TypeError`，会原地打转——实测同一个文件读了 16 次）；
答案键（`source`）**不序列化**。再补一条自证：每次重复的判据带唯一 canary，
跑完扫事件流和工作区，**命中即判该次重复被污染**并从样本里剔除。
（[bench.md](bench.md) §十九.11、§十九.12，已修；守卫测试 `tests/test_heldout.py`）

**第十三处（2026-11-11，隐藏判据的契约被提前公布；**试过修、改坏了、已回退**）**：
第十二处把判据的**实现**藏住了，可判据的**要求**还印在模型的验收文本里：

```
- (L1/held_out) pct() must return the payable factor for **every** discount tier:
                the platform fee of the tier is deducted on top of the discount …
```

这一句就是**第一道任务要学的那条规则**。和第十二处**同性质**：
答案在模型动手之前就到了，只是这次不是源码，是一句说明书。
修法试了两条（要求只在失败反馈里给 + 第一道任务的 prompt 不带契约文件），
**2 reps 试点（`.membench-fee17p`）把装置改坏了**：模型**连读 24 次**同一个文件、
一次都不写 ⇒ 第一道任务 `blocked` ⇒ 没有教训；第二道任务也从"一次写对"变成"改不对"
（配对样本 0）⇒ **回退**。
⇒ **教训的产出率由模型行为决定，装置控制不了**：契约在手时它有时一次做对
（实测 3/8 次没有教训），契约不在手时它卡住（也没有教训）。
⇒ 装置能做的只有：**把产出率测出来并报出来**（`lesson_paired_reps`），
以及**别把这个数字藏起来**。
（[bench.md](bench.md) §十九.13；守卫测试
`tests/test_membench.py::FeeFamilyTest::test_the_first_task_does_carry_the_contract_file`）

**后果**：在修好这几处之前，"记忆有效"这个结论**只在脚本模型上成立**；
真实模型上它连"被读到"都做不到。修好之后"两条路径收益重合"的结论才第一次有了真实模型的数据，
但它只在"模型一次就做对"的任务族上成立。

**而且即使装置改成"记忆有机会省事"，它也没省下来**（2026-11-11 第二轮，`contract` 族 8 reps）：
把约定藏到 prompt 之外、让"读那个文件"成为必要动作之后，
**三臂的第一步仍然都是 `read shop/helpers.py`**——事实里已经写清了函数名、文件、
契约和旧行为，模型**还是要打开源文件核对**。

⇒ **对会读代码的模型，记忆替代不了读代码，只能替代"试错"。**
记忆系统的价值必须按这个边界来设计：要省的那部分，得是**只有试错才能得到**的知识。

**但连这条结论都得打折**（2026-11-11 第三轮）：把行为从事件流回读之后才发现，
**那一族的契约是猜得出来的**——可见测试钉住 `total([100,200],10) == 270`，
模型推出 `pct(10) == 0.9` 就顺手推出 `pct(20) == 0.8`，
于是那次核对是**自愿的**（不核对也能过），记忆压根没有东西可省。
**所以"没测到收益"这句话，有一半是装置自己的毛病**（[bench.md](bench.md) §二十一）。
新的任务族 `fee`（平台费按档位取值，`pct(10)==0.88` 推不出 `pct(20)==0.75`）
把知识变成**必需**的，重新测。

**测出来的结论，以及它带来的新边界**（`fee` 族第四版装置，
`.membench-fee16`，8 次重复、三臂都有效、canary 零污染）：
**已验证事实让模型少查 50% 的档位表（72 → 36 次，8 次里 7 次更少）**——
这是记忆在这个装置上**唯一测得出来**的收益。
**但成本口径测不出来**：步数 -27%、tokens -21%，而**同 prompt 的 A/A 地板是 ±48% / ±52%**
⇒ 落在地板之内，不能当收益报。
⇒ 新的失效模式（这一轮最贵的）：**报告效应量之前，必须先量同 prompt 的 A/A 地板**。
上一轮宣称的"-45% tokens"从来没对照过地板——它同时被污染过、也被自己的地板证伪了。
⇒ 所以新的失效模式是：**记忆会把"发现错误"的能力一起省掉**（上一轮那条仍然成立）：
记忆系统的价值不能只按"省了多少步"算，
**要按"省掉的动作里有没有发现错误的那部分"算**——
这直接指向"要不要给事实臂也配一条护栏"。

**"教训臂"这一侧：注入了，但没测出收益**（第四版装置）：
8 次重复里它**带着教训真跑了 5 次**（rep 4~8，92/133 个 prompt，教训全部是模型自己写的），
可它**没替掉任何核对**（查档位表 72 → 92，**反而更多**），成本也没省（-4%，噪声内）。
⇒ 原因不是"教训没用"，而是**教训携带的是契约转述（"漏了平台费，总价 270 而非 264"），
不是知识本身**——转述替代不了查表。
⇒ 而且**产出率装置控制不了**：契约在 prompt 里时模型有时一次做对（3/8 次没有教训），
契约不在 prompt 里时它**卡住**（连读同一个文件 24 次、任务 `blocked`、也没有教训）
⇒ 两条路都通向"没有教训"（[bench.md](bench.md) §十九.13，改法被试点否掉并回退）。
⇒ 所以**"模型写的教训没收益"这句话，这轮的数据证明不了**：
既不能当"没用"，也不能当"有用"。
教训注入率必须和效果一起报，不能只报效果。

**这一轮还暴露了十个装置缺口**：
①**安全闸门会悄悄抽掉一个臂的处理**：模型用了带 `;` 的子 shell 命令 →
需要人工批准 → 基准里没人批准 → 第一道任务被拦下 → **那一轮没有教训可注入**；
而事实臂不受影响（事实是程序按"全量测试通过"存的）。
②**模型调用失败会被算成任务失败**：8 次重复里 8 次运行死于 provider 报错
（0 tokens、2 次调用、仓库没被碰过）；而且**失败不整齐**——对照臂多出 1 次有效运行，
所以配对口径必须**只取所有臂都有效的重复**，不能手打"作废 rep 6/7/8"。
③**报告生成器在部分数据上除零**（[bench.md](bench.md) §十九.10，已修）：
报告每个 rep 之后都重写一遍，遇到"首个 rep 的对照臂没有 tokens"就抛 `DivisionError`，
**整轮已经付费的实验被带走**。
④**判据命令的相对路径**（[bench.md](bench.md) §十九.11，已修）：
第一道任务永远不通过 ⇒ 没有教训 ⇒ 教训臂测的是空气。
⑤**判据没有被真正藏住**（[bench.md](bench.md) §十九.12，已修）：
模型能用 shell 读到判据源码（答案就在里面），失败反馈的 traceback 也会把答案带出去。
⇒ ⑤这一条最要命：**它污染的是已发布的那批数字**，不是"少测了一次"。
所以"装置自证"必须包含**判据的可达性**：canary 扫事件流，命中即作废该次重复。
⑥**外部调用的挂死会带走整轮实验**（[bench.md](bench.md) §十九.10，已修）：
客户端原来只有 socket 超时，而 socket 超时管的是"一次读卡住多久"——
服务器一直慢慢吐字节，它就一直被重置。实测一次调用**挂了十五分钟**，
TCP 连接还在，整轮 campaign 停在那里等。
现在 API 调用有**总时限**（默认 180 秒）：到点就放弃这次调用（记成"模型调用失败"，
该次运行退出样本），而不是无限等。
⇒ **外部依赖的调用必须有总时限**，这个时限不能由对端的行为决定。
⑦**隐藏判据的契约被提前印在验收文本里**（[bench.md](bench.md) §十九.13，
**试过修，改坏了，已回退**）：把契约从验收文本里拿走、并把契约文件从第一道任务的
prompt 里拿走 ⇒ 模型**连读 24 次**同一个文件、一次都不写 ⇒ 第一道任务 `blocked`
⇒ 没有教训；第二道任务也从"一次写对"变成"改不对"（配对样本 0）。
⇒ **教训的产出率由模型行为决定，装置控制不了**：契约在手时它有时一次做对（3/8 次没有教训），
契约不在手时它卡住（也没有教训）——两条路都通向"没有教训"。
⇒ 装置能做的只有：**把产出率测出来并报出来**（`lesson_paired_reps`），
以及**别把这个数字藏起来**。
⑧**发布前的门自己有洞**（[bench.md](bench.md) §十九.14，已修）：
①canary 扫描按报告里的臂名拼日志文件名，而第一道任务的日志叫 `events_setup_N`，
于是**第一道任务从来没被扫过**——而模型读判据源码正是发生在那儿
⇒ "没有污染"当时没有根据；②"L1 失败"这一列在报告里是去重口径、在事件流里是
逐次口径，门拿它们对比永远对不上；③"无效回复"逐次表里没有列，门却拿它当不一致。
⇒ **门必须先在自己身上跑一遍**：一个只报"通过"的门，和没有门一样危险。
⑨**装置从来没量过自己的噪声地板**（本轮补上，`membench --verify` 的 `NOISE FLOOR` 段）：
同 prompt 的两臂（A/A 对照就藏在"注入率"里）实测相差
**±48% 步数 / ±52% tokens / ±21% 查表**，
而上一轮宣称的效应量是 -45% tokens ⇒ **效应比地板小 ⇒ 不可报**。
⇒ **报效应之前先报地板**；小于地板的一律报成"测不出来"。
⑩**外部依赖还多一种失败模式**：provider 的**配额用尽**返回 429
（"已达到 Token Plan 用量上限"），不是超时、不是挂死，
现象是**立刻失败**（0.3s）而不是慢慢卡住——
⇒ 装置必须把"provider 失败"和"模型做错"分开标记（本项目已有 `model_failed`），
而且**外部额度也是实验设计的一部分**：额度耗尽时这一轮就只剩已跑完的那些重复。

**缓解**：新增记忆能力必须在这套装置上**不劣于**基线；
真实模型的数字必须同时报**注入命中率**（`带教训的 prompt` / `带事实的 prompt` 两列）
和**到验收通过的步数/tokens**（总步数会被模型做完之后的反复确认顶满，不是成本口径）；
还必须报**行为**（从事件流回读"模型有没有去查那个隐藏约定"）——
**结果没差、行为也没差，才能说"这类任务上记忆没有可测收益"**；
否则测的还是"库里有东西"，不是"东西被用上了"。

**还有一条纪律（本轮血买的）**：**报告里的数字必须由脚本从原始产物重算**，
不能手打——2026-11-11 一次手抄就在同一份文档里错了 4 处（多剔了对照臂一次有效运行、
把两个不同分母加在一起、注入率差了一倍）。
现在有 `python -m planloop membench --verify --dir <run> --report <report.md>`：它从事件流重算每一个发布的数字，并和机器报告**逐列交叉核对**，
不一致就非零退出（实现 `planloop/membench_verify.py`，守卫 `tests/test_membench.py::VerifyTest`）。
它同时报**被污染的重复**（canary 命中）并把它们从样本里剔除。

**还有一条纪律（这一轮血买的）**：**判据必须自己证明自己没被读到**。
"仓外"不等于"读不到"——`run` 走 shell，模型能读任何文件；
而失败反馈的 traceback 还会把答案原样打印出来。
所以判据从 stdin 喂给 python（磁盘上根本没有它），
每次重复带唯一 canary，跑完扫事件流和工作区，命中即作废该次重复。
**一个会污染结果的装置缺陷，比一次没测出来更贵**：它污染的是已经发布的数字。

## 四、成本与预算

### 12. token 估计是估算

脚本模型按 `字符数 / 3.2` 估算，真实 API 才返回准确 usage。
**后果**：离线实验里的"成本"是相对值，不能当账单。

### 13. 预算只在总量上硬

阶段配额是软借用（记录但不阻断），所以"规划阶段烧掉 30%"会悄悄发生。

## 五、不适用的场景

| 场景 | 为什么不适合 |
|---|---|
| 单步任务（改一个变量） | 分解与调度只增加延迟和漂移 |
| 无客观验收的创作类任务 | 只能靠 L2/C 级证据，"成功"无法证实 |
| 完全无人值守的长任务 | 第 20 步的方向性错误没人纠正 |
| 需要实时响应的交互 | 每节点多轮 ReAct，延迟不可接受 |

## 六、假设清单

实验与结论建立在这些假设上，换环境需要重新验证：

1. 任务可重复执行（仓库可重置），否则无法统计。
2. 失败有可读的错误文本，否则签名机制失效。
3. 验证命令是廉价且确定的（秒级测试）。
4. 模型稳定：同一 prompt 的行为方差不会主导结果。
5. 演示里的"模型"是脚本化的——**它证明的是机制正确，不是模型能力**。
