# Benchmark：B0 / B1 / B2

> 状态：**已实现**（`planloop/bench.py`，`planloop bench`）。
> 最近一次结果：[bench-results.md](bench-results.md)（脚本模型，seed=7，reps=10）。

## 一、要回答的问题

不是"框架好不好"，而是：**在同样的模型、同样的预算下，验证 + 重试是否比"多发几次、投票"更划算？**

三个配置只差一件事：

| 配置 | 一次尝试 | 验证 | 重试 | 说明 |
|---|---|---|---|---|
| **B0** | ✅ | ❌ | ❌ | 模型说完成就是完成 |
| **B1** | 5 次 | ❌ | ❌ | 取产物指纹的多数票（自一致性） |
| **B2** | ✅ | ✅ | ✅ | planloop：验收不过则重试（上限 2） |

成功与否由**独立 oracle**（跑测试）判定，**不由被测配置自评**——否则 B2 一定赢。

## 二、三个任务

| 任务 | 初始状态 | 正确做法 | 典型错误 |
|---|---|---|---|
| `fix_discount` | 折扣算反，测试红 | `sum * (100-pct)/100` | `sum - pct` |
| `add_feature` | 缺 `mul()`，现有测试绿 | 加实现 + 加测试 | 顺手把 `add` 改坏 |
| `rename_symbol` | `fmt_name` 待改名 | 定义与调用点一起改 | 只改定义，调用点报 ImportError |

每个任务都有 `correct` / `wrong` 两套产物，模型每次尝试以概率 `p_correct` 选中其中一套——这是整个 benchmark 里唯一的随机源。

## 三、怎么跑

```bash
planloop bench --reps 10 --seed 7 --p-correct 0.6
planloop bench --reps 20 --out docs/bench-results.md
```

参数：

- `--reps`：每个"任务 × 配置"单元格重复次数；
- `--p-correct`：脚本模型单次尝试的正确概率（模拟模型能力）；
- `--seed`：固定随机源，保证可复现。

## 四、结果（seed=7, reps=10, p=0.6）

| config | 成功率 | 平均 tokens |
|---|---|---|
| B0 | 63% | 134 |
| B1 | 73% | 668 |
| B2 | 80% | 1246 |

读法：

- **B0 ≈ p**（0.6），符合预期，说明度量没跑偏；
- **B1 花 5 倍 token 只换来 +10pp**——自一致性在"错误模式系统化"时收益有限；
- **B2 花 ~9 倍 token 换 +17pp**，且它的重试是**有依据的**（验收失败才重试），不是盲目多发。

三者成本不可直接比：B2 每步都要跑验收。真正的对照是**同等预算下谁的成功率高**——按 token 折算，B2 在 ~1.9× B0 的成本下拿到了 B1 用 5× 成本才达到的效果。

## 五、这个数字证明了什么，没证明什么

**证明了**：

- harness 正确：B0 的成功率收敛到 `p_correct`，说明没有偷偷帮忙；
- oracle 独立：成功由测试决定，不由模型自述；
- B2 的重试确实救回了部分失败（63% → 80%）。

**没证明**：

- 真实模型的 `p_correct` 分布是未知的，也不会像这里一样"每次独立重掷"；
- 脚本模型的错误是**固定的两套**，真实模型的错误更多样，验证器召回率才是真正的天花板；
- token 是估算值（`字符数 / 3.2`），不是账单。

## 六、接真实模型

设好三个环境变量后，把 `AttemptModel` 换成 `OpenAICompatModel` 即可（`bench.py` 里只依赖 `complete()`）：

```bash
export PLANLOOP_MODEL=...            # 模型名
export PLANLOOP_BASE_URL=...         # OpenAI 兼容端点
export PLANLOOP_API_KEY=...
```

改造点已经做完：`bench.MODEL_FACTORY` 是唯一开关，CLI 用 `--real` 设置它。

```bash
# 端点已验证可用（MiniMax）
python -m planloop bench --real --model MiniMax-M3.1-Flash \
    --reps 1 --tasks fix_discount --n-best 2 --out .demo/real-bench.md
```

**注意**：真实模型下 B0/B1/B2 的差异会显著受"验证器召回率"支配。验证器漏判时，B2 会自信地交付错误结果——这一点必须在报告里写明，不能被成功率掩盖。

## 七、真实模型的实测（2026-11，MiniMax-M3.1-Flash）

### 修上下文之前

| 配置 | 任务 | 结果 | tokens | 用时 |
|---|---|---|---|---|
| B0 | `fix_discount` | ✅ 成功 | 2445 | 45s |
| B2 | `fix_discount` | ❌ 失败 | 5644 | 101s |

**这组数字不能用来证明"验证没有用"，因为两组拿到的上下文不对等：**

| | 提示里有什么 | 模型要做什么 |
|---|---|---|
| B0/B1 | 任务目标 + **所有文件的完整内容** | 直接写正确代码 |
| B2（planloop 执行器） | 节点目标 + 验收条件 + 工具协议，**没有文件内容** | 先 `read` 再改，多绕几步 |

这是 bench 暴露出的真实缺陷：**比较不是同一条件**。B2 输在上下文，不是输在验证。

### 修上下文之后（同一任务、同一模型、同一 seed）

| 配置 | 结果 | tokens | 用时 |
|---|---|---|---|
| B2 修前 | ❌ 失败 | 5644 | 101s |
| B2 修后 | ✅ 成功 | **1229** | **5s** |

一次注入把 B2 从"失败 + 5.6k token + 101s"变成"成功 + 1.2k token + 5s"。

**这是本次最有价值的发现**：瓶颈不在"验证太重"，而在"模型不知道要改什么"。执行器原来只给目标和验收条件，模型得先自己 `read` 文件——多出来的步数、上下文与失败，全部由此产生。

### 完整对照（3 任务 × 2 重复，MiniMax-M3.1-Flash）

| 配置 | 成功率 | 平均 tokens | 说明 |
|---|---|---|---|
| B0 单发 | 6/6 | 4296 | — |
| B1 三次投票 | 6/6 | **11168** | 3 次尝试，成本约 2.6× |
| B2 验证+重试 | 6/6 | **2577** | 上下文注入 + 提前停止 |

原始报告：[bench-real.md](bench-real.md)（B0/B2 部分有效）、[bench-b1.md](bench-b1.md)（B1，使用修正后的判定）。

**读法（重要）**：

1. **三个配置都 6/6**——这三个任务对这个模型太简单，指标退化成"成本比较"，看不到成功率的差别。要证明"验证能提高成功率"，必须换更难的题（当前任务一轮就过，重试根本没被触发）。
2. **B1 在这里纯属浪费**：成功率没提升，token 是 B0 的 2.6 倍。这正是"自一致性只在模型会犯错时才划算"的实证。
3. **B2 最便宜（2577）不是因为它有验证，而是因为上下文注入让它 2–3 步就结束**。验证只是让它"敢于提前结束"。

### 评测器的一个真 bug（已修）

第一版 B1 用"产物字符串是否等于参考实现"判定成功，结果真实模型全部被判失败——因为它是用 `sum(prices) * (1 - pct/100)` 通过测试的，和参考的 `sum(prices) * (100 - pct) / 100` 不一样。

**成功必须由 oracle 判定**，这条原则我自己在 B1 里破了。修法：把胜出的产物重新落盘，跑测试判定。修完 B1 从 2/6 变成 6/6。

这个 bug 说明一件事：**脚本模型永远写"标准答案"，所以它能掩盖所有"只认标准答案"的评测缺陷。**真实模型一上来就把这个洞挖出来了。

修法（已完成）：

1. `ProblemSpec.context_files`：任务声明需要哪些文件；
2. 执行器**每步重新读取**这些文件并注入上下文（不是启动时读一次，否则节点刚写的文件下一步就是旧的）；
3. 上限 8000 字符，超出截断，避免把上下文撑爆。

```python
spec = ProblemSpec.from_dict({
    "goal": "...",
    "context_files": ["shop/pricing.py", "tests/test_pricing.py"],
    ...
})
```

两侧现在看到同样的文件内容；B2 额外多一份验收条件，这是它该有的差异。

### 加难度之后（跨模块兼容 + 干扰文件）

新增两个任务：

| 任务 | 难点 | 错误模式 |
|---|---|---|
| `compat_rename` | 改名同时保留 `area` 兼容别名（隐含约束） | 只改名不保留别名 → `tests/test_compat.py` ImportError |
| `noisy_fix` | 仓库里有 `app/legacy/pricing.py` 干扰文件 | 改了废弃实现，真实现没动 |

结果（M3.1-Flash，2 重复）：

| 配置 | 成功率 | 平均 tokens |
|---|---|---|
| B0 | 100% | 3388 |
| B1 | 100% | 10444 |
| B2 | 100% | 2627 |

换更弱的 `MiniMax-M2.5-highspeed` 单跑一轮：仍然 **B0 2/2、B2 2/2**，B0 4000 tokens，B2 2692。

**结论：任务还是不够难。**这个模型家族对"小仓库、单文件、有明确测试"的改动能稳定一次做对，所以三个配置的成功率拉不开，指标仍然是纯成本。

这本身是一个有用的结论：**验证的价值只在该出错的场景里显现**。当模型一次就对时，验证只是多花 token 的保险。

### 成本结论（跨 5 个任务、2 个模型）

| 配置 | 平均 tokens | 相对 B0 |
|---|---|---|
| B0 单发 | ~3800 | 1.0× |
| B1 三次投票 | ~10400 | 2.7× |
| B2 验证+重试 | ~2650 | **0.7×** |

B2 反而最省。原因不是验证，是两件事：

1. **上下文注入**让模型 2–3 步就改完（B0 要 4–6 步，每步都重发全部文件）；
2. **早期停止**——验收通过就结束，不会继续"再检查一下"。

## 八、长链任务：一次被推翻的结论

> **2026-11-10 更正**：本节最初写的是"B0 0/6、B2 3/3，验证把成功率从 0 提到 100%"。
> 复查发现 B0 的失败有一半是评测器的问题——B0 的输出上限是 1200 token，多文件的一次性回复被截断，
> JSON 解析失败，看起来像"模型没做对"。上限提到 4000 后，同一族任务上 B0 变成 6/6。
> **"0/6 vs 3/3" 不能作为验证价值的证据。**下面是更正后的数据。

`long_rename_chain`：12 个文件，需要改 7 个（core + 包 `__init__` + 5 个调用点），
2 个节点计划（T1 改名 + 别名，T2 更新调用点）。

一开始这题"错答案也能过"——因为兼容别名放在 `core.py` 里，漏改的调用点照样能 import。
改成"别名只放 `ledger/__init__.py`"、并加一个 `tests/test_admin.py` 真正 import 被漏改的模块之后，
错误分支才真正失败。**题目设计错了，benchmark 会给出虚假的乐观结论。**

结果（MiniMax-M3.1-Flash，**修正输出上限之后**，16 次样本/配置）：

| 配置 | 成功 | 平均 tokens |
|---|---|---|
| B0 | **16/16** | 14837 |
| B2 | **16/16** | 21176 |

**两个配置都全过，B2 贵 43%。**"验证救回失败"在这个任务族上不成立——因为这个模型一次就能改对。

（这轮跑到 32/36 次时接口返回 502 中断，两个配置都已各自跑满 16 次，结论不受影响。
顺带给 `OpenAICompatModel` 加了 3 次重试 + 退避——之前一个 502 就能让整轮跑到一半崩掉。）

之前那版"B0 0/4"是在输出上限 1200 token 时测的：模型一次性回复 7 个文件被截断，
JSON 解析失败，被记为"失败"。**同一个现象既可以解释成"模型不行"，也可以解释成"评测器不行"，必须先排除后者。**

**这是整个 benchmark 里第一次"验证改变了结果"**：单发与投票都漏掉至少一个调用点，
B2 在第 2 个节点被验收拦下、带着失败信息重试，最终成功。

代价也真实：B2 的 token 是 B0 的 3–4 倍。当时判断主要原因是整仓库文件每步重发。

**于是做了按节点收窄上下文**（TaskNode.context_files：T1 只看 3 个文件，T2 只看 6 个），
结果是一次**负结果**：

| 方案 | 成功 | tokens |
|---|---|---|
| 整仓库注入 | 3/3 | 9727 / 14408 |
| 按节点收窄 | 3/6 | 7482 – 16297（均值 ≈ 12k） |

token 没有明显下降，成功率也没有变好。原因看清楚了：**成本大头不是文件列表长度，而是每一步都把整个上下文重发一遍**。
一个节点跑 4 步，就是 4 倍；收窄文件只是把每份体积降了一点。

于是又试了节点会话化的前提假设：**缓存**。

### 缓存实测（MiniMax）

同一个 1518 token 的前缀连发两次：

| 调用 | prompt tokens | 命中缓存 |
|---|---|---|
| 第 1 次 | 1518 | 199 |
| 第 2 次 | 1518 | **1517（100%）** |

缓存是真实存在的，且命中部分通常按折扣计价。问题在于**我们的提示词一直在变**：

| 布局 | 缓存命中率 | 结果 |
|---|---|---|
| 文件每步全量注入（现状） | 33% | 成功 |
| 文件只在节点第一步注入 | 44–56% | **0/2 失败** |

第二种明显更省 token，但模型看不到文件就不改对——它会凭记忆写出过时代码，而且不会主动 
ead。

**这是本次最实在的一个权衡：缓存效率与正确性在这里是反向的。**
真正的解法不是少发文件，而是**只发变化**（diff / 增量），或者让模型在需要时精确 
ead（需要提示词里明确要求）。

所以本节结论：
1. 缓存可用，但目前只能吃到 1/3；
2. 粗暴地少发文件会牺牲正确性；
3. 增量文件上下文（只发改过的部分）是下一步，不是会话化。

样本量仍然很小（B0 4 次、B2 3 次），**不能说"验证把成功率从 0 提到 100%"**，只能说"在这道题上，方向是一致的"。

## 九、已知局限

1. 六个任务里有五个仍偏小（3–5 个文件）；长链任务只有 1 道。
2. B1 的"投票"用产物指纹，真实场景里往往没有可比对的指纹。
3. 没有统计显著性检验——每个格子只有 1–6 个样本。
4. 成本只算 token，没算墙钟时间与工具调用费用。
5. B2 的上下文注入是整仓库级别的，文件多时成本被放大。
6. **B0 按定义看不到命令输出**（`_act` 只把文件内容回灌给模型），所以本基准测的是
   "**强制**验收"的价值，不是"验收"本身的价值。B0 不是"会自己验证的 agent"。
   真正的对照是 B1 vs B2——两者都拿不到失败反馈，区别只在于 B2 会带着失败信息重试。
7. 老任务的判据是工作区里的测试文件，模型能改自己的判卷（见第十一节）。

## 十、要让成功率拉开，还差什么

| 方向 | 具体做法 | 为什么现在没做 |
|---|---|---|
| 加长链 | 5–10 节点 DAG，跨模块依赖 | B0/B1 没有"计划"概念，只能整段写；对照不公平，需要先定义 B0 的长任务形态 |
| 加隐含约束 | 20+ 文件、约定散落在文档而非测试里 | 需要更真实的仓库样本 |
| 注入故障 | 让模型以固定概率产生系统性错误 | 那是脚本模型已经在做的事 |
| 换更弱模型 | 已经试过 M2.5-highspeed，仍然一次过 | 需要再低一档的模型 |

**在拿到"会失败"的样本之前，任何"验证提升成功率"的说法都只是推断，不是测量。** 这句话应该写在报告最上面。

## 十一、判据不再由被测者决定（2026-11-10）

这一节是本轮对 **harness 本身** 的修正，与模型无关。

### 11.1 模型可以改自己的判卷

老任务的判据是 `python -m unittest discover -s tests -q`，跑在工作区里——
**和工作区里那个模型被要求一起编辑的测试文件是同一批文件**。于是：

```python
# 模型写的"测试"
def test_mul(self):
    self.assertTrue(True)
```

判据绿了，功能其实没实现。`add_feature` 这类"要模型自己补测试"的任务，
判据等于由被测者自己写、自己改。**这是评测器缺陷，不是模型缺陷**——
和第八节"B0 0/4 是输出上限截断"是同一类错误。

### 11.2 改成工作区外的held-out 判据

`Task.hidden_tests` 把判分测试写到**工作区之外**（`<temp>/oracle`），
判据变成 `python -m unittest discover -s "<temp>/oracle" -q`，`cwd` 仍是工作区，
所以被测包照样能 import。关键点：

- `Tools._resolve` 把所有读写锁在工作区根目录，**模型读不到也改不到**判分测试；
- `tools.write()` 指向工作区外会抛 `ToolError`，这一点有单测守着；
- 判据成为节点的 **acceptance**（不只是端到端 success_criteria），
  这样 in-loop 的 L1 复核和"带着失败信息重试"用的都是 held-out 判据，
  **失败输出里才有真正的诊断信息**。

判分测试写好之后，两条分支必须一过一挂，否则题目本身是坏的：

| 任务 | correct | wrong |
|---|---|---|
| `add_feature_checked` | 过 | 挂 |
| `division_convention` | 过 | 挂 |
| `legacy_copy` | 过 | 挂 |
| `divide_zero_hidden` | 过 | 挂 |
| `mean_empty_hidden` | 过 | 挂 |

这条自检是**单测**（`tests/test_bench_oracle.py` 会遍历所有带 held-out 判据的题），
不是手工检查——题目以后加错会直接挂测试。

### 11.3 顺带修掉的两个 harness 缺陷

| 缺陷 | 症状 | 修法 |
|---|---|---|
| B1 投票只比 `task.correct` 里列出的文件 | 真实模型改的其它文件在物化胜出者时被丢掉 | 指纹改用整份工作区快照（`workspace_snapshot`），排除 `__pycache__` |
| B0 的 prompt 只注入 4000 字符上下文，B2 注入 8000 | 大仓库题上 B2 白拿一半上下文 | B0 预算提到 8000，与 `execute._files_block` 对齐 |
| `PROTOCOL` 宣传 `read` 动作，harness 却没实现 | 模型发了 `read` 什么也没发生，白费一步 | 删掉这个动作，不宣传没实现的东西 |

> B0 预算从 4000 提到 8000 之后，**本文件第八节之前的 B0/B2 数字不再严格可比**
> （大仓库题上 B0 拿到的东西变多了）。老数字保留原样，标注为改动前。

### 11.4 新增的实验轴：采样温度

`planloop bench --temperature` 现在能把模型的采样温度调上去。
目的是制造**真实**的首轮失败（而不是靠判据作弊）：

```bash
python -m planloop bench --real --model MiniMax-M3.1-Flash \
    --temperature 1.0 --reps 2 --configs B0 --out .demo/temp1.md
```

结果（M3.1-Flash，B0，共 12 次）：

| 任务族 | 样本 | 成功 |
|---|---|---|
| 简单题（fix_discount / add_feature / compat_rename / noisy_fix） | 8 | **8/8** |
| 链任务（long_rename_chain / rename_chain_3 / rename_chain_5 / rename_chain_8） | 4 | **4/4** |

**温度 1.0 也造不出失败。** 采样噪声这条路对"小仓库 + 明确测试"的任务族无效——
模型不是靠运气做对的，是它真的做对了。

## 十二、让模型"自己宣布完成"失效的题

上面所有题都有一个共同前提：**模型看得见判据**。于是它能一次做对。
要测出验收的价值，得有一类题——**模型按自己的理解做完了、也真的做对了，
但它理解的那件事不是要求的那件事**。

这类题的判据必须是 held-out 的（模型看不见），否则等于把答案告诉它。

### 两道新题

| 题 | 机制 | 模型为什么容易错 |
|---|---|---|
| `division_convention` | `calc/README.md` 写明"除零统一抛 `ValueError`"；可见测试只测 `add` | 模型写了 `a / b`，`ZeroDivisionError` 冒出去了；它自己的测试没覆盖这个分支，**它认为自己做完了** |
| `legacy_copy` | `app/pricing.py` 与 `app/legacy/pricing.py` 是同一份逻辑的两份拷贝；仓库里的测试只指向**归档的那份** | 模型照着可见测试修好了归档副本就收工，**线上走的那份没动** |

两题都设了 `judge_visible=True`——B0 的 prompt 里也会给出判据命令，
**两边知道怎么被判，区别只在于拿不拿得到失败反馈**。

### 三类"模型会宣布完成、但不算完成"的题

前面两道的机制是"约定写在文档里"——模型读了，就做对了。
但真正想让验收层显形，要换成另一类机制：**判据的命令是公开的，判据的断言不是**。

这正是 planloop 的产品形态：节点验收把命令给模型看（`node.acceptance_text()`），
但断言在判分测试里，模型读不到。于是模型只能按自己的理解写，
**只有验收失败输出能告诉它真相**——而这恰恰是"强制验收"独有的通道。

| 题 | 判据里多了一条模型看不见的要求 | 模型第一次会交付什么 |
|---|---|---|
| `divide_zero_hidden` | 除零必须抛 `ValueError`（不能是 `ZeroDivisionError`） | `return a / b` —— 对自己的测试来说完全正确 |
| `mean_empty_hidden` | 空列表的均值必须是 0 | `sum(values) / len(values)` —— 对自己的测试来说完全正确 |

判据可见性对两边一致（`judge_visible=True`，B0 的 prompt 里也有验收命令），
**区别只在于拿不拿得到失败反馈**。

**跑之前的预测（先写下来，跑完再对账）**：

- B0 挂——它看不到断言，也拿不到失败输出；
- B1 也挂——投票是在同一批盲猜里取多数，三次都看不见那条要求；
- B2 过——失败输出（`ValueError not raised` / `ZeroDivisionError: division by zero`）
  就是缺失的那条要求，重试一次就能补上。

如果这个预测成立，它就是这套东西第一次拿到"验证把失败救回来"的**测量**，
而不是推断。

### 结果

**预测命中。** M3.1-Flash，held-out 判据，两道题，累计 28 次样本：

| 配置 | 成功 | 平均 tokens | 平均用时 |
|---|---|---|---|
| B0 单发（盲） | **0/10** | 14445 | 104s |
| B1 三次投票（盲） | **0/9** | **39576** | 283s |
| B2 验证 + 带失败信息重试 | **9/9** | **8322** | 44s |

Fisher 单侧精确检验：B2 vs B0 `p = 1.1e-5`，B2 vs B1 `p = 2.1e-5`。
方向无歧义，但样本仍小（10/9/9）、只有一道任务族、只有一个模型。

逐次明细（第一轮）：

| 任务 | 配置 | 结果 | tokens | 用时 |
|---|---|---|---|---|
| `divide_zero_hidden` | B0 | ❌ | 4087 | 21s |
| `divide_zero_hidden` | B1 | ❌ | **41434** | 239s |
| `divide_zero_hidden` | B2 | ✅ | **7704** | 31s |
| `mean_empty_hidden` | B0 | ❌ | 16624 | 97s |
| `mean_empty_hidden` | B1 | ❌ | **41300** | 326s |
| `mean_empty_hidden` | B2 | ✅ | **8176** | 36s |

**这是这个 benchmark 第一次测出"验证把失败救回来"。** 三个事实同时成立：

1. **B0 会交付坏东西。** 它写的实现对自己写的测试完全正确——`return a / b`、
   `sum(values) / len(values)`——但真实判据要求的是 `ValueError` 与空列表返回 0。
   没有强制验收，这就是上线的东西。**8 次全挂。**
2. **B1（投票）救不回来。** 三次独立尝试，三次都看不见那条要求，
   多数票仍然是错的。它花了 **4.1 万 token 平均值**，是 B2 的 **5 倍**，
   成功率是 0。**"多发几次"不能替代验收。**
3. **B2 救回来了，而且最便宜。** 验收失败输出（`ValueError not raised` /
   `ZeroDivisionError: division by zero`）就是那条缺失的要求，
   带着它重试一次就补上了——**8321 token 平均**，只有 B1 的五分之一。**7 次全过。**

对照关系很清楚：**B0 和 B1 都拿不到失败反馈**（B1 是三次盲猜取多数），
B2 拿得到并且会重试。差别不在"跑几次"，在"失败之后有没有反馈通道"。

完整报告：[bench-hidden.md](bench-hidden.md)。

### 另两种机制：失败了（模型比预期更仔细）

同一轮里还试了两种**依赖模型读文档/看全仓库**的陷阱，**两个都没触发**：

| 题 | 机制 | 结果 |
|---|---|---|
| `division_convention` | 约定写在 `calc/README.md` | B0 4/4 全过 |
| `legacy_copy` | 可见测试指向归档副本，线上走另一份 | B0 4/4 全过 |

B0 一次没挂——**模型把 README 里的约定读进去了，两份拷贝也都改了**。
报告：[bench-trap.md](bench-trap.md)。

**这两道题不能用来制造失败，只能作为"模型比预期更仔细"的记录。**
真正制造失败的是第十二节那两道：**要求不在模型看得见的任何地方**。
这也说明"约定写在文档里"这种做法，拦不住一个会读文档的模型——
**能被拦住的只有"约定本身不可见、只有判据知道"的那一类。**


### 这个结果能推广到什么程度

**不能**推广到"验证普遍提升成功率"。它成立的前提有三个，缺一不可：

1. 模型**看不见**判据的断言（真实判据比模型自己的测试更严）；
2. 失败输出**足够诊断**（"ValueError not raised" 直接指向要改的地方）；
3. 一次重试**够用**（补一条分支而已，不是重做整个功能）。

还有一个必须说清的混淆：**B2 不是"纯验证"，是整个执行器**（上下文注入 + 每步复核 +
带失败信息重试 + 提前停止）。第十五节的消融已经把这个问题拆开：
**同一个执行器关掉强制验收（B2C）后，成功率从 6/6 掉回 0/6，和 B0 无统计差别。**
也就是说这批任务上的成功率收益**全部归因于失败反馈通道**，不归因于执行器的其余部分。

统计上方向是无歧义的（B2 vs B0：Fisher 单侧 p=1.1e-5；B2 vs B1：p=2.1e-5），
但样本仍小（10/9/9）、只有一道任务族、只有一个模型。

### 成本不是常数

"验证要花多少钱"没有单一答案，实测跨三个任务族是三个数：

| 任务族 | 场景 | B0 | B2 | B2 / B0 |
|---|---|---|---|---|
| 短任务（5 题 × 2 模型） | 模型一次就对 | ~3800 | ~2650 | **0.70×**（更省） |
| 长链任务 | 模型一次就对 | 14837 | 21176 | **1.43×**（更贵） |
| hidden 判据（本次） | 模型本来就会错 | 14021 | 8321 | **0.59×**（更省） |

**所以"验证是纯成本"是错的说法**，正确的是：

- 模型一次就对、且任务短 → 上下文注入 + 提前停止让 B2 反而**更便宜**；
- 模型一次就对、但任务长链 → 每步重发整个仓库，B2 **贵 43%**；
- 模型本来就会错 → 一次失败 + 一次带诊断的重试，比盲写一遍**更省**（0.59×）。

**验证的成本随任务形态和模型表现变化，收益则完全取决于模型会不会自己宣布完成。**

**所以准确的结论是两条，不是一条：**

- 在"模型会宣布完成、但不算完成"的场景里，**强制验收 + 带失败信息的重试**
  把成功率从 0 拉到 100%，且比盲投票省 5 倍 token——**这是测量，不是推断**；
- 在"模型一次就对"的场景里，验证**不必然是成本**：短任务更省，长链任务贵 43%。
  **验证的价值只在该出错的场景里显现**，这一点现在有两侧的实测支撑了。

## 十四、这一轮到底测出了什么

1. **采样噪声不是失败源。** 温度 1.0、12 次 B0，全过。
2. **"模型看得见判据"的任务族，模型一次就做对。** 12 次 B0、全部成功——
   验证层没有触发机会，B2 的成本随任务形态变化（短任务 0.7×，长链 1.43×）。
3. **能被测量的验证价值，来自"模型自己判断做完了"这类失效。**
   第十二节测到了：B0 0/10、B1 0/9、B2 9/9（p=1.1e-5），且 B2 比 B1 省 4.8 倍 token、
   比 B0 还省 42%。
4. **评测器的三个真实缺陷被修掉了**（第十一节）：判据可被被测者修改、
   B1 投票丢编辑、B0 上下文预算只有 B2 一半。
5. **消融把因果归到了失败反馈上**（第十五节）：同一个执行器关掉强制验收（B2C）
   后是 0/6，和 B0 无统计差别（p=1.00）；加回强制验收是 6/6（p=1.1e-3）。
   **上下文注入、工具、提前停止都不改变这类失效上的成功率。**
6. **贡献来自失败输出里的"诊断"，不是"重试机会"**（第十五节 B2D）：
   告诉模型"你失败了"、再给它一次机会，但不说错在哪——0/5；
   同一个执行器，把真实 traceback 喂回去——6/6（成功那次的 8 个 prompt 里有 7 个带着 traceback）。

## 十五、消融：把"上下文注入"和"失败反馈"的贡献拆开

第十二节测到的是 **B2 整体**（上下文注入 + 每步复核 + 带失败信息重试 + 提前停止）
对 **B0**（单发、盲）的优势。但 B2 不是"纯验证"，所以那 0/8 → 7/7 里，
**有多少来自"验证"，有多少来自"上下文注入"，当时没有分开**。

### B2C：同一个执行器，关掉验证

新增配置 `B2C`（`bench.py: run_b2c`）：

| | B0 | B2C | B2 |
|---|---|---|---|
| 执行方式 | 单发 JSON 动作 | **planloop 执行器** | planloop 执行器 |
| 上下文注入 | prompt 里一次性给 | **每步重新注入** | 每步重新注入 |
| 工具 | 有 | 有 | 有 |
| 提前停止 | 无 | **有** | 有 |
| 节点验收 | 无 | **永不失败的桩** | held-out 判据 |
| 失败反馈 | 无 | **无** | 有 |
| 失败后重试 | 无 | **无** | 有（上限 2 次） |
| 谁判定成功 | held-out 判据 | held-out 判据 | held-out 判据 |

B2C 与 B2 的**唯一差别**是：节点的验收判据换成一条永远通过的桩命令。
于是 in-loop 的 L1 复核永远通过，模型永远看不到失败，也永远拿不到重试；
但上下文注入、工具、提前停止、最终判定全部不变。

**三个比较各自回答一个问题：**

- **B0 vs B2C** —— 执行器本身有没有用？（上下文注入/工具/提前停止的贡献）
- **B2C vs B2** —— 失败反馈通道有没有用？（这就是"验证"本身）
- **B2C ≈ B0** 时，**B2 的优势就归因到失败反馈，而不是执行器的其他部分**。

### 跑之前的预测

**B2C 应当和 B0 一样全挂**（模型拿不到那条隐藏要求）。
如果 B2C 反而全过，那说明 B2 的优势来自上下文注入而不是验收——
**"验证有价值"这个结论就要推翻**。

（消融语义本身有单测守着：`B2C` 的模型永不被"纠正文本"重新掷骰，
`B2` 会被——见 `tests/test_bench_oracle.py::AblationTest`。）

### 结果

**预测命中。** M3.1-Flash，两道 held-out 判据题，同轮对照（reps=3，每格 6 次样本）：

| 配置 | 成功 | 平均 tokens | 说明 |
|---|---|---|---|
| B0 单发 | **0/6** | 14585 | 无反馈、无重试 |
| B2C 同执行器但不做强制验收 | **0/6** | 7234 | 有上下文注入/工具/提前停止，**无失败反馈、无重试** |
| B2 强制验收 + 带失败信息重试 | **6/6** | 8360 | 有失败反馈、有重试 |

Fisher 单侧精确检验：B2 vs B0 `p = 1.1e-3`，B2 vs B2C `p = 1.1e-3`，
B2C vs B0 `p = 1.00`（**两者没有差别**）。

**这就把因果归到了失败反馈上：**

- **执行器本身没有用。** B2C 拥有和 B2 完全一样的上下文注入、工具、提前停止——
  成功率仍然是 **0/6**，和单发的 B0 **统计上无差别**。
  **"上下文注入让模型更准"这个说法，在这批任务上不成立。**
- **加回强制验收，B2 从 0/6 变成 6/6。** 唯一的差别就是
  "模型有没有被告知失败、并且被允许重来一次"。
- 成本上 B2C 甚至比 B0 便宜一半（7234 vs 14585）——
  **执行器省下来的 token 买不到成功率**；B2 比 B0 便宜 43%，
  却是唯一成功的配置。

**所以之前那句"没法把上下文注入的贡献从失败反馈里拆出来"，现在拆开了：
在这个任务族上，成功率 100% 归因于失败反馈通道，0% 归因于执行器的其余部分。**

完整报告：[bench-ablation.md](bench-ablation.md)。

### 消融不能说明什么

1. **只在"判据断言不可见"这一类任务上做过。** 执行器在别处可能有用
   （比如长链任务上省 43% token），只是在这类失效上**不改变成功率**。
2. **B2C 的 prompt 里验收命令是桩命令**，B2 里是判据路径。
   两者对模型的信息量相同（路径里没有断言），但严格说不是逐字节相同。
3. **样本量仍是 6/格**，只覆盖一道任务族、一个模型。
4. ~~**没拆"重试次数"**~~ → **已由 B2D 拆开**（见下一小节）：B2D 有重试但失败输出不带诊断。

### B2D：告诉它失败了，但不告诉它哪错了

第十五节那版消融把"失败输出"和"重试机会"一起去掉了（B2C 既不反馈也不重试）。
**B2D** 只拆开这两个因素：

| | B0 | B2C | **B2D** | B2 |
|---|---|---|---|---|
| 节点验收 | 无 | 永远通过 | **安静判据**（失败但不说原因） | held-out 判据 |
| 模型被告知失败了吗 | 否 | 否 | **是** | 是 |
| 模型知道失败原因了吗 | — | — | **否** | 是 |
| 有重试机会吗 | 否 | 否 | **是** | 是 |
| 成功判定 | held-out | held-out | held-out | held-out |

"安静判据"是一个放在工作区外的脚本：它照常跑 held-out oracle，失败时**只写一行**
`ACCEPTANCE FAILED`，不附带任何测试输出。

跑之前写下的预测（两条互斥，必须有一条中）：

- **B2D ≈ B2C** → 关键不是"再给一次机会"，而是**第二次机会要知道错在哪**；
- **B2D ≈ B2** → 只要重来一次就够，失败输出不是关键。

**实测中的是第一条**（B2D 0/6，与 B2C 同级；B2 6/6）。

（语义有单测守着：安静判据的输出里不允许出现 `AssertionError`、测试文件名或任务名。
见 `tests/test_bench_oracle.py::QuietJudgeTest`。）

### 判据污染检查

"held-out"这个说法有个前提:**模型真的看不见判据**。但执行器有 shell 能力，
而沙箱"不是隔离边界"（README 原话），所以模型理论上可以用 `run` 把判据读出来。

三道防线：

1. **工具层挡住直接读**：`Tools._resolve` 拒绝工作区外的路径，
   `read`/`write` 都会抛 `ToolError`。
2. **判据路径不泄漏**：判据放在工作区外的临时目录，模型只能从验收命令里
   看到路径，看不到内容。
3. **运行后扫描**：每道题的判据文件首行带一个注释标记
   （`# planloop-oracle:<task key>`），unittest 永远不会打印它，
   但模型如果把判据抄进工作区就会带上它。跑完扫描一遍，**抄了就作废该次运行**。

> 这道防线是被一次真实崩溃逼出来的（见第十六节）：模型确实顺着 prompt 里的
> 路径去读判据了。

### 四臂结果

带状态记录的那次运行（24 格，1 格被策略中断、已剔除）：

| config | 成功 | 平均 tokens | 平均执行器调用 | 样本 |
|---|---|---|---|---|
| B0 | 0/6 | 12484 | 8.67（模型调用） | 6 |
| B2C | 0/6 | 7121 | 1.00 | 6 |
| B2D | 0/5 | 14809 | 2.00 | 5 |
| B2 | 6/6 | 8973 | 1.00 | 6 |

单侧 Fisher 精确检验：**B2 vs B2D p=2.2e-3**、B2 vs B2C p=1.1e-3、B2 vs B0 p=1.1e-3；
**B2D vs B2C p=1.00**、B2D vs B0 p=1.00。

另外两次独立复现（早期 harness，没有状态记录，见第十七节）给出完全一样的格局：
B0 0/6、B2C 0/6、B2D 0/6、B2 6/6。

被剔除的那一格：**B2D / divide_zero_hidden**，模型在第一条命令里写了嵌套 shell
（`$(`/反引号），触发策略的 `subshell` 确认规则 → 需要人工批准 → 整轮被拦下，
**执行器一次都没跑完**。这一格没有测到验收行为，所以不计入成功率——
详见第十七节：这正是上一版 harness 会把它误算成"一次失败"的原因。

完整报告：[bench-ablation2.md](bench-ablation2.md)。

### 机制：模型到底看见了什么

光看成功率说不清 B2D 为什么是 0/5——有两种解释：

1. **安静判据让重试根本没触发**（那 B2D 测的还是 B2C，只是换了条路径）；
2. **重试触发了，但失败信息里没有诊断**，模型改不对（那 B2D 测的才是"有没有诊断"）。

这两种解释导出完全不同的结论，必须先分掉。方法是把模型实际收到的 prompt 抓下来。

**B2D 臂**（真模型，16 次模型调用）：

| prompt | 看到 traceback | 只看到"失败" | 带 supervisor 纠正 |
|---|---|---|---|
| 0-7（第一次节点执行） | 否 | 是 | 否 |
| 8-15（重试） | 否 | 是 | 是 |

重试确实发生了（节点执行 2 次，第二次带 supervisor 纠正），
但 16 次调用里模型一次也没看到过 `ZeroDivisionError` / `FAILED (...)`，
只看到 `exit=1 (want 0)` 和 `ACCEPTANCE FAILED: the acceptance criteria are not satisfied.`。

**B2 臂**（真模型，两道题各跑一次，都是成功）：

| 任务 | 成功 | 节点执行 | 模型调用 | 带 traceback 的 prompt |
|---|---|---|---|---|
| divide_zero_hidden | 是 | 1 | 8 | **7 / 8** |
| mean_empty_hidden | 是 | 1 | 8 | **7 / 8** |

这两行是整份报告的关键：**B2 的成功不是"模型一次就写对"**——
8 次调用里有 7 次带着真实 traceback，模型是**看着报错改对**的。
而"节点执行 = 1"说明纠错发生在**同一次节点执行内**（执行器每步都做 L1 检查，
失败输出直接进下一轮 prompt），根本没用上 scheduler 的重试。

对照起来看：

- **B2**：模型被反复告知"哪里错了"（真实 traceback）→ 改对了 → 成功；
- **B2D**：模型被反复告知"失败了"（没有诊断）→ 改不对 → 失败；
- **B2C**：模型完全不知道验收存在 → 失败。

所以 B2D 的 0/5 是第二种解释：**重试本身不是关键，失败输出里带不带诊断才是关键**。
而 B2C 从来不失败（1 次执行、0 次纠正），它测的确实是"没有反馈"这一档。

同一套语义也由离线探针（脚本化模型，不烧 API）交叉验证，
并由 `tests/test_bench_oracle.py::FeedbackChannelTest`（3 项）守着：
B2 必须把 traceback 交给模型、B2D 必须不交、B2D 必须仍然被纠正、B2C 必须从未被纠正。

## 十六、实验反过来挖出一个产品 bug

跑四臂消融时，**B2D 那一臂崩了**——不是 API 抖，是代码问题：

```
planloop.tools.ToolError: path escapes workspace:
  C:\Users\...\Temp\tmpd4nb9sah\oracle\judge.py
```

链条是这样的：

1. B2D 的节点验收命令里带着判据的**绝对路径**（判据在工作区外）；
2. 这条命令会出现在模型的 prompt 里（`node.acceptance_text()`）；
3. **模型顺着这个路径去 `read` 判据文件**；
4. `Tools._resolve` 正确地拒绝了（路径在工作区外）；
5. 但 `ToolError` **没有被任何一层接住**——它穿过 executor、穿过 scheduler、
   一路抛到 CLI，**整轮运行直接死掉**。

### 这比"模型想偷看判据"严重得多

问题不在于模型想读判据（那是可接受的竞争行为，读到了就作废该次运行）。
问题在于：**模型的一个普通动作（读一个越界路径）就能杀死整轮长任务。**
长任务跑了几十步、烧了几万 token，一次 `read` 越界就全部作废——
这正是这个项目要解决的"长任务跑不完"问题本身。

### 修法

`execute.py` 的动作分发现在把 `ToolError` 当成**一次失败的动作**：

```python
except ToolError as exc:
    # A refused action (path outside the workspace, unreadable file)
    # is ordinary agent behaviour, not a fatal error: report it and
    # let the model correct itself.
    obs = Observation(kind or "action", False, 2, "", str(exc))
```

模型会看到"这次 read 失败了"，然后自己换个路径继续。

回归测试在 `tests/test_pipeline.py::RefusedActionTest`，**验证过它在无修复时确实变红**
（`git stash` 掉修复后跑一次，红；恢复后跑一次，绿）。

### 顺带确认过的两件事

- `DeniedAction` / `NeedsApproval` 在 scheduler 里**本来就有**专门的 blocked 报告，
  不受影响；`SandboxError` 只在启动配置错误时抛（docker 缺失），也是该快速失败。
- 这次崩溃同时证明：**模型确实会去读 prompt 里出现的路径**。
  所以"held-out 判据"必须有污染扫描兜底（上一节），不能只靠"模型看不见"。

**教训**：benchmark 不只是用来测模型的——**它自己会把 harness 的 bug 逼出来**。
如果只看"成功率"这一个数字，这次崩溃会被当成"实验失败"而丢掉，
而不是变成一个产品 bug 的报告。

## 十七、这一轮又挖出来的三个测量缺陷

四臂消融跑第二遍时，抓到三个**"报告在说谎"**的地方。它们都不是模型的问题，
是**仪表**的问题——而且每一个都会把结论往有利于假设的方向推。

### 17.1 报告里的"污染检查"是默认值渲染出来的

合并脚本用 `Outcome(config, task, ok, tokens, 1, secs)` 重建记录：
`contaminated` 吃了 dataclass 的默认值 `False`，`attempts` 硬编码 `1`。
于是报告里那句

> 判据污染检查：24/24 次运行未在工作区里发现 held-out 判据的副本

**根本不是测出来的**——是"没人填"渲染出来的。数字看着严谨，语气笃定，结论却是伪造的。

修法：合并脚本从日志行的 `CONTAMINATED` 标记里读；缺字段就报错，不补默认值。

### 17.2 "重试次数"这一列在真实实验里是占位符

`Outcome.attempts` 取自 `getattr(model, "attempts", 1)`。
真实模型对象（`OpenAICompatModel`）**根本没有这个属性** → 恒为 1。
也就是说"重试次数"从头到尾没被测过——而 B2D 的结论**完全取决于**这个量：
到底是"没重试"，还是"重试了但没诊断"？

修法：改从 scheduler 的 `result.outcomes` 长度取（执行器被调用了几次），
它与模型实现无关；脚本化模型和真实模型都能测。

### 17.3 "跑了但失败"和"根本没跑完"被算成同一件事

`max(1, len(outcomes))` 把"节点跑了一次就失败"和
"整轮被策略中断（需要人工批准 / 动作被拒）、一次都没跑完"压成同一个数字 1。
这两件事的结论完全不同：后者**根本没测到验收行为**，
把它算成一次失败会**偏向**消融假设（B2D 看起来更糟）。

实际抓到的例子（带状态记录的那次运行）：

```
[B2D] divide_zero_hidden: success=False tokens=5892 attempts=0 status=blocked 28s
       blocked=high-risk action needs approval: evaluates a nested shell command
```

模型在第一条命令里写了嵌套 shell（`$(` / 反引号）→ 触发策略的 `subshell`
确认规则 → 需要人工批准 → 整轮被拦下，**执行器一次都没跑完**。
旧版 harness 把它记成"执行器调用 1 次、失败"——
也就是把一次**根本没测到验收行为**的中断，记成了 B2D 的一次失败。

修法：`Outcome` 增加 `status` / `blocked` 两个字段，日志行里带上；
报告把被中断的格子单独列出，**不计入**成功率比较
（`is_interrupted()` 按原因分类：只有"需要批准 / 被策略拒绝 / 执行器调用 0 次"
才算中断，`end-to-end acceptance failed` 和 `execution failure persisted over N attempts`
都是**普通结果**，必须留在比较里）。

> 这三个缺陷的共同点：**它们都不会让程序报错，只会悄悄改变一个数字。**
> 第一遍跑出来的"0/6 vs 6/6"看着完全没问题——正是这种沉默让它们活到了第二遍。

## 十八、判据本身够不够尖：故障注入集

前十七节测的都是**反馈**：有验收、有诊断的失败输出，模型能不能改对。
但还有一个问题这套实验答不了：**判据自己够不够尖**？
判据若对什么都放行，bench 会给出 100% 的成功率，而且理由完全错误。

`planloop faults` 补的就是这一半：

```bash
python -m planloop faults --out docs/fault-recall.md
```

装置：对每个任务注入一批**已知**缺陷（mutant），分别用两个判据跑——
**强判据**（工作区外的 held-out oracle，模型读不到、改不到）与
**弱判据**（工作区里模型自己写的那份可见测试，模型能改）。

三道对照防止判据「假装很尖」：

1. 正确实现必须通过两个判据；
2. 语义等价的改写（neutral）必须通过；
3. 每个 mutant 都要和正确实现做**行为探针**对比——行为一样的是
   **等价 mutant**（注入的其实不是缺陷），不计入召回率分母。

结果（2026-11-11，3 个案例 × 33 个缺陷）：

| | 强判据（仓外 oracle） | 弱判据（模型自己写的测试） |
|---|---|---|
| 召回率 | **33/33 = 100%** | 13/33 = 39% |
| 过杀 | 0 | 0 |

**20 个缺陷只被强判据抓住**——这就是"模型自己写测试"换不来的部分，
也是仓外判据存在的量化理由。

> 第一轮跑出来有 1 条"漏检"，分诊后发现是**等价 mutant**：
> 注入的缺陷本身语义没变（`if TAX_RATE < 0` 的分支永远不触发，
> 但后面的正确计算还在）。判据没错，是注入无效。
> 现在这三种状态由行为探针自动分诊，不再靠人眼。

完整明细见 [判据召回率](fault-recall.md)；主张层面的含义见
[项目主张分析](analysis.md)。

## 十九、换成真实模型之后：记忆这条路上有十四处静默失效

第十八节测的是判据。第十九节换了个问题：**把记忆价值度量从脚本模型换到真实模型**，
结果第一件事不是"记忆有没有用"，而是**记忆这条路上有十四处一测就死的环节**。

十四处里十二处都有同一个特征：**不报错、不崩，只是让"记忆"变成只写不读的一本账。**
脚本模型一个都没碰到——脚本模型每次都返回干净的 JSON，触发条件也是我们自己写死的。

> 第十处（19.10）不在记忆链路上，而在**报告生成器**上：
> 它在"数据还没成形"时除零，把整轮已经付费的实验带走。
>
> 第十一处（19.11）和第十二处（19.12）更靠后：**判据自己坏了**——
> 一处让第一道任务永远不通过（于是压根没有教训可测），
> 一处让判据**根本就没被藏住**（于是测到的是模型翻文件的本事，不是记忆）。
>
> 第十四处（19.14）也不是模型的问题，是**发布前的门自己有洞**：
> canary 从没扫过第一道任务的日志（模型读判据源码恰恰发生在那儿），
> 而"没有污染"这句话当时**没有根据**。
>
> 第十三种修法（19.13）是本节唯一一个**"试过、改坏了、回退"**的：
> 把契约从验收文本里拿走，模型就从"失败后修复"变成"反复读同一个文件直到超预算"——
> 教训的产出率由**模型行为**决定，装置控制不了。

### 19.1 教训生成给的 500 token 预算，被推理模型的思考吃光了

`propose_lesson` 用 `model.complete(prompt, max_tokens=500)` 去问模型"这次失败能总结出什么教训"。
真实模型是推理模型，**思考 token 和回答 token 同一个池子**：

| max_tokens | finish_reason | reasoning_tokens | content |
|---|---|---|---|
| 500 | `length` | **499** | **0 字符** |
| 4000 | `stop` | 3325 | 1213 字符（完整教训） |

500 预算下模型**一个字都没吐**，只有 2231 字符的思考内容。
`model.complete` 抛 `RuntimeError`，`propose_lesson` 的 `except (ValueError, RuntimeError)`
把它吞掉，退化成兜底教训：

```json
{"summary": "failure repeated: AssertionError: 0.1 != 0.9 ...", "cause": "", "fix": "worked around it",
 "trigger": {"error_patterns": ["AssertionError:\\ 0\\.1\\ !=\\ 0\\.9 ..."]}, "guard": null, "strength": "advisory"}
```

**没有原因、没有做法、没有触发条件、没有护栏**——而且 `source` 还写着 `"model"`，
因为 `source="model" if model is not None else "heuristic"` 只看"有没有传模型"，不看"模型到底说了什么"。

修法：预算提到 4096（实测这条教训要 3667 completion token）；`source` 改成只有模型真给出了
summary 才算 `model`，兜底时记 `heuristic` 并把失败原因写进 `evidence`；
教训提示词里要求命令型护栏的 `must` 必须是机器可读格式（见 19.3）。

### 19.2 触发条件里只要带 error_patterns 或 commands，教训**永远检索不到**

`Trigger.matches` 的规则是"每一段都要匹配"。但执行期构造的上下文**只有目标和文件**：

```python
ctx = MemoryContext.from_workspace(f"{node.goal}", self.workspace, commands=[])
# commands=[] ，error_text="" —— 永远没有命令历史，也永远没有错误文本
```

于是：

- 触发条件里的 `error_patterns` → 要在一段空字符串里匹配 → **必然不匹配**；
- 触发条件里的 `commands` → 要在一段空字符串里匹配 → **必然不匹配**。

而 `LESSON_PROMPT` 明确让模型"至少给出 files / goals / error_patterns / commands 其中之一"，
**真实模型照做**：它给出的触发条件同时带了 files、goals、commands、error_patterns。
结果这条教训**一次都没进过 prompt**——实测 `教训出现在 0/12 个 prompt 里`，
事件流里连一条 `memory_hit` 都没有。记忆库变成了只写不读的账本。

修法：**上下文给不出的段不参与否决**。判据是"能不能查"而不是"是不是假"——
查不了的段是**未知**，不是**不匹配**。同时保留一条底线：触发条件里如果**只有**
error_patterns（其他段都没有），仍然要求错误文本，否则谁都能匹配。

改完之后，同一条教训的注入从 `0/12` 变成 `12/12`。

### 19.3 模型写的护栏 `must` 不是机器可读格式 → 判据**永远通过**

19.1 里那次教训，模型给的护栏是：

```json
{"kind": "command", "spec": "python -m unittest discover -s tests -q",
 "must": "exit status 0 with all tests passing"}
```

`parse_must` 找的是 `key=value`，这句话里**一个等号都没有** → 解析结果是空字典 →
"没有约束" → **判据恒为真**。

一个**永远通过**的护栏比没有护栏更坏：报告会说"硬护栏已注入"，而它什么都拦不住。
而且它在入库前的自检里是"通过"的（仓库当时确实是绿的），所以自检也发现不了。

修法：`Verifier._check_l1` 里，命令型判据的 `must` 解析不出任何键时**回落到 `exit=0`**
（命令型判据的默认语义），而不是"无约束即通过"；同时把这句话写进 `verdict.detail`，
报告里看得见。教训提示词也补了格式要求。

### 19.4 模型写的正则有未闭合分组 → 检索链路直接崩

上面那条提示词改进之前，模型给出的 goals 正则是这样的：

```
"(?i)(pricing|discount|total"      <- 少一个右括号
```

`re.search` 对它抛 `re.error`，而检索路径上没有任何保护——
**一条坏正则把整条记忆检索打挂**（异常一路冒到执行器，节点直接失败）。

修法两头都堵：写入时 `Trigger.from_dict` 把非法正则**丢掉**（`sanitized()`），
匹配时 `_first_match` 对非法模式**跳过而不是抛出**。另外在教训提示词里点名了这个坑
（"a `goals` regex that only matches the goal you can see right now makes the
lesson unusable"），改完之后模型给出的触发条件变成了
`goals=["(?i)(pricing|discount|percentage|percent|subtotal)"]`、
`files=["**/*pricing*.py", ...]`——**能命中下一个任务的措辞**。

### 19.5 模型把 `goals` 写成字符串 → 触发条件变成通配

模型有时不写列表，直接写一个字符串：

```json
"trigger": {"goals": "(?i)(pricing|discount|percentage|percent|subtotal)"}
```

解析时按"取列表里的每一项"处理，于是**字符串被逐字符拆开**，
触发条件变成 `['i','p','r','i','c','i','n','g','|',...]`——
一个只要目标里出现任意一个字母就命中的**通配**。

报告里能直接看见它：`goals=['i', 'p', 'r', 'i', 'c', 'i', 'n', 'g', '|', ...]`。

后果有两层：这一条教训会**到处触发**（无关任务也命中），
而真正的风险是**它把整套触发逻辑变成不可信**——报告里那一列看起来像"很具体的正则"，
实际是乱码。

修法：解析时如果拿到的是字符串，就当成**一个**模式（`_as_list`），
不是逐字符拆。

> 前五处缺陷的共同点，和第十七节那三个一模一样：**它们不会让程序报错，只会悄悄改变一个数字。**
> 脚本模型那套装置一个都测不出来——脚本模型不思考，触发条件也是我们手写的。
> **结论：机制在脚本模型上"有效"，不等于它在真实模型上"活着"。**
> 换模型不是把数字跑一遍，是把整条链路重新验一遍。

### 19.6 推理模型**只交思考过程、不交答案** → 教训退化成兜底模板

第二十节之后换了新任务族，第一条教训就退化成了兜底模板
（`source: heuristic`，`summary: "failure repeated: AssertionError: 270.0 != 264"`）。
证据里写着原因：

```
lesson model unusable (ValueError: no JSON object in model reply:
'We need answer JSON only. Need infer lesson. Task Chinese: fix shop/pricing.py ...')
```

模型**想了，没答**：`content` 是空的，客户端退回到 reasoning 通道，
于是回复是一段散文，里面**一个 `{` 都没有**。
JSON 解析失败 → 教训退化成兜底模板 → `fix` 变成 `"worked around it"`、
触发条件只剩 `error_patterns` → **第二道任务里一次也没被检索到**
（实测教训出现在 **0/13** 个 prompt 里）。

而兜底模板的触发条件只有 `error_patterns`，执行期上下文**永远没有错误文本**
（这正是 19.2 那条）——所以它必然检索不到。
**两处缺陷叠在一起，这条教训就是死的，而且报告里看不出来。**

修法两处：

1. 模型适配层把"只有 reasoning"标出来（`Completion.reasoning_only`），
   教训生成**再试一次**，并附上"只回 JSON、不要思考"的严格要求
   （`LESSON_RETRY_SUFFIX`）；两次都不行才回落兜底。
2. 报告新增一行**「模型自己写的教训 X/Y 条」**，让退化**看得见**——
   不然读者只会看到"教训 8/8 条都在"，以为机制是通的。

守卫测试：`tests/test_memory.py::LessonRetryTest`
（散文优先 → 重试后拿到真教训 / 两次都散文 → 回落且**记录了失败**）。

### 19.7 教训生成器**看不到修复长什么样** → 它会编一个原因出来

修好 19.6 之后，教训是模型写的了，`source` 也不再撒谎。
但内容是**错的**：

> 教训：The shared `pct()` helper quantized a requested 12% discount to the 10% tier…
> 做法：Edited `shop/helpers.py` so `pct(discount_pct)` computes the exact
> remaining-price multiplier, **1 - discount_pct / 100, for every supported
> discount tier**;

而模型**真正写进文件的是带档位表的那一版**（`value >= 20 → 0.05`，否则 `0.02`）。

根因：教训提示词里的"什么让它过了"只有

```
commands: python -m unittest ... ; wrote 239 chars to shop/helpers.py
summary: edited shop/helpers.py
```

——**只有文件名和一行摘要，没有文件内容**。
于是模型只能**猜**修复是什么，然后写下一个**自信的错误**。

这比没有教训更糟：这条教训的触发条件是
`files=['shop/*.py'], goals=['(?i)(pricing|discount|percentage|percent)']`，
**会命中第二道任务**，把一个错误的"做法"直接灌给模型。

修法：调度器把**改过之后的文件内容**一起交给教训生成器
（`scheduler.py::_fix_excerpt`，有长度上限），
提示词里也写明"`fix` 必须描述**文件里实际是什么**，不是你猜的改法"。

守卫测试：`tests/test_memory.py::FixExcerptTest`。

> **19.6 和 19.7 合起来是一条更一般的教训**：
> **一条教训的价值取决于它写的是不是真的。**
> 而"模型自己写的"既不保证**有**（19.6：退化成模板），
> 也不保证**对**（19.7：编一个原因）。
> 这直接关系到 `memory.py` 和 `memdb.py` 该不该合并：
> **已验证事实（`memdb.py`）是把**外部观测**写下来的，
> 模型写的教训（`memory.py`）是模型对观测的**转述**——
> 转述会掉信息、会编。**
> 两者不是"收益重合"，是**保真度不同**。

### 19.8 顺带修掉的一个隐患：失败诊断可能被挤出 prompt

执行器每一步都把验收失败写进 observation，但 **prompt 只带最后两条**。
也就是说，模型自己的两个动作就能把"为什么失败"顶出窗口——
而模型最需要的就是这个。

修法：失败文本单独**钉住**（`blackboard.record_rejection`），
只要验收没过就一直出现在 prompt 里（`execute.py::_observations_block`）。

> **要说清楚这条不是某个故障的解释**：实测那次"重复读同一个文件 23 次"的循环，
> **失败文本当时还在窗口里**——所以循环的原因是模型卡在"记忆说的"和"文件写的"之间反复对账，
> 不是被挤出窗口。钉住失败文本是一条**保证**（保证它永远在），不是那次循环的解释。
> 守卫测试：`tests/test_pipeline.py::RejectionStaysVisibleTest`。

### 19.9 第九处：模型写的 `shop/**/*.py` 触发条件**永远匹配不上**

第三版装置（`fee` 族）跑完之后回读事件流，发现教训臂在 5 次配对重复里
**只在 2 次真的带着教训跑**（rep 1、rep 3）。查原因，不是模型不听话，
是**触发条件永远匹配不上**。

模型给 rep 5 写的触发条件是：

```json
"files": ["shop/**/*.py"]
```

而匹配用的是 `fnmatch.fnmatch`。`fnmatch` **没有 `**` 语义**：
它把每个 `*` 换成 `.*`（连 `/` 一起吃掉），但**把 `/` 保留成字面量**。
于是 `shop/**/*.py` 要求 `shop/` 和文件名之间**还得有一层目录**：

```python
fnmatch.fnmatch("shop/helpers.py", "shop/**/*.py")   # False
fnmatch.fnmatch("shop/sub/x.py",   "shop/**/*.py")   # True
```

工作区里根本没有子目录，所以这条触发条件**一次都没命中过**。
和 19.4 那个未闭合正则是**同一类病**：模型写的模式被当成可信输入，
匹配层悄悄什么都不匹配，教训于是**写进去就再也没出来过**。

修法：文件 glob 改成**按路径段匹配**，`**` 表示"零段或多段"
（`memory.py::_match_glob`）。守卫测试
`tests/test_memory.py::DoubleStarGlobTest`（5 条，含 `**` 不该越界的情况）。

> **这条同时暴露了一个测量纪律问题**：教训臂这轮**没有构成一次有效的
> "带教训 vs 不带"对比**——3/5 的重复里教训臂其实等价于无记忆对照。
> 所以"教训没收益"这句话这轮**证明不了**，必须重测。
> 教训注入率必须和效果一起报，不能只报效果
> （[记忆值不值（`fee` 族）](memory-value-fee.md) §六.4）。

### 19.10 第十处：报告生成器在**部分数据**上除零，把整轮实验赔进去

这一处不是记忆链路上的，是**装置自己**的：报告在**每个 rep 之后**都会重写一遍
（这样跑到一半崩掉也不会带走前面的结果），于是它必须扛得住"数据还没成形"的状态。

2026-11-11 重跑 `fee` 族时，第一个 rep 的对照臂模型调用失败 ⇒ tokens 为 0 ⇒
报告里算百分比那行 `/(c_tok)` 直接抛 `DivisionError` ⇒
**整个 8 reps  campaign 在模型调用已经付过费之后死掉**，只剩 rep 1 的事件流。

这和前九处是同一个家族的病：**不是"算错一个数字"，而是"一个本该正常的状态
把整轮实验带走"**。前九处让记忆变成只写不读的一本账，这一处让**报告**变成
一碰就碎的玻璃。

修法：百分比的分母为 0 时输出"（对照臂还没有可用数据）"而不是崩；
守卫测试 `tests/test_membench_report.py::PartialDataReportTest`（3 条：
首个 rep 无对照数据、全空数据、零 token 臂不得产出 `nan`）。

> **顺带一条纪律**：长实验的**报告生成必须与实验解耦**——
> 报告写不出来不能让实验停下来。写报告的代码路径要有"数据不完整"的分支，
> 而不是假设数据完整。

**同一族的第二个病例：模型调用挂死**（2026-11-11，同一轮重跑时撞上）。

客户端原来只有一个 **socket 超时**（`urlopen(timeout=120)`）。socket 超时管的是
"一次读操作卡住多久"——**服务器只要一直慢慢吐字节，它就一直被重置**。
实测：一次 chat completion **挂了十五分钟**，TCP 连接还在 `Established`，
进程 CPU 0.8 秒、无子进程——整个 8 reps campaign 就停在那里等它。

（同一个时刻手工打同一个 API，1.1 秒就返回了——所以不是"服务挂了"，是"这一次调用没回来"。）

修法：给 API 调用加**总时限**（`deadline`，默认 180 秒，可由
`PLANLOOP_MODEL_DEADLINE` 调）——请求跑在自己的**守护线程**里，
主线程 `join(deadline)`，到点就放弃这次调用（记成"模型调用失败"，
该次运行作废、退出样本），而不是无限等下去。
守卫测试 `tests/test_model.py::ModelCallDeadlineTest`。

> **纪律**：**外部依赖的调用必须有总时限**，而且这个时限不能由对端的行为决定。
> socket 超时是"对端不说话的时长"，总时限才是"我愿意等多久"。

### 19.11 第十一处：仓外判据的命令用**相对路径** ⇒ 第一道任务永远不通过

修完第九处（`fnmatch` 没有 `**` 语义）之后重跑 `fee` 族，第一个 rep 就红了：

```
ImportError: Start directory is not importable: '.membench-fee11\\oracle'
```

根因在 `_prepare_oracle`：它把判据写到 `<base>/oracle/`，然后把
`-s "<base>/oracle"` 拼进命令——而 `base` 是**相对路径**（`.membench-fee11`）。
这条命令是在**工作区里**执行的（cwd = `<base>/repo`），于是 `-s` 被解析成
`<base>/repo/.membench-fee11/oracle`——**那个目录不存在**。

后果不是"判据红"那么简单：判据挂在第一道任务的**节点验收**上，
它永远不通过 ⇒ 第一道任务永远完不成 ⇒ **教训压根不会产生**（教训只在"失败→被修复"之后才写）
⇒ 教训臂测的还是空气。

> 这一处是**潜伏**的：同一份代码在上一轮（`--dir` 传绝对路径）跑得好好的，
> 换了个相对路径就整轮作废。**同一份装置代码，在两种调用方式下结果完全不同**——
> 这本身就是"装置不可复现"的信号。

处置：那一轮（`.membench-fee11`）在 rep 1 就止损作废。修法不是把路径拼对，
而是**判据不再是一条命令**（见 19.12）：它不再有路径，也就没有路径能拼错。

### 19.12 第十二处：仓外判据**根本没被藏住**——模型用 shell 读到了判据源码

判据的"仓外"一直只是**工作区之外**。但工作区锁只管 `read`/`write` 两个工具，
**`run` 走的是 shell**——而 shell 能读进程够得着的任何文件：

```
cd /d "D:\github\planloop\.membench-fee9\repo" && dir && type "...\oracle\r1_oracle_1.py"
```

回读 `fee` 族（8 reps）的全部事件流，这类动作有 **3 次**：
`setup_1`、`setup_4`、`R2_none_5`。而判据源码里写的就是**答案**
（`pct(10) == 0.88`、`pct(20) == 0.75`、`total(...) == 198.0`）。
于是那几次重复里，模型**不用去查档位表也能拿到答案**——
测到的就成了"模型翻文件的本事"，不是记忆。

还有**第二条通道**：验收失败文本会喂回给模型，而 unittest 的 traceback
**会打印失败的那一行源码**——那一行正是写着答案的那行。实测：

```
  File "<held-out criterion>", line 9, in test_member_discount_is_applied_after_the_discount
    abs(total([100, 200], 10, 20) - 198.0) < 1e-7,
```

`198.0` 就是第二道任务的答案。**反馈通道也在泄题。**

修法（三条一起上，缺一条就还会漏）：

1. **判据不再落盘**：它被喂给 `python -`（标准输入），**任何时刻磁盘上都没有它**——
   不是"在仓外"，是"根本不存在文件"。
2. **从标准输入来的程序，traceback 里没有源码行**——反馈通道自动堵死。
   失败信息还在（断言消息按约定不含数字），所以模型依然知道**该改什么**。
3. **判据的"存在形式"和"答案"分开**：新 kind `held_out`，
   `spec` 是**不含数字的要求描述**（模型看得见：失败必须说清在查什么，
   只给一个 `exit=1` 或者裸 `TypeError`，模型会原地打转——实测同一个文件读了 16 次），
   `source` 是答案键，**不序列化**（持久化的计划里只有判据 id，没有答案）。

再补一条**自证**：每次重复的判据源码里带一个唯一 canary，
跑完扫一遍事件流和工作区——**命中即判该次重复被污染**，
`membench --verify` 会把它从样本里剔除并明确报出来。
"判据被藏住了"从此是**可查的**，不是一句声明。

守卫测试：`tests/test_heldout.py`（9 条：判据不落盘、失败输出不含答案、
判据仍能判红判绿、payload 不进 prompt、不进持久化计划、canary 能查出泄漏）。

### 19.13 第十三处：隐藏判据的**契约被提前印在验收文本里**——**试过修，改坏了，回退**

第十二处把判据的**实现**藏起来了，但判据的**要求**还留在模型的验收文本里。
把渲染出来的验收文本打出来（`fee` 族 R1）：

```
- (L1/command)  "…python.exe" -m unittest discover -s tests -q must=exit=0
- (L1/held_out) pct() must return the payable factor for **every** discount tier:
                the platform fee of the tier is deducted on top of the discount,
                so one tier's factor says nothing about the next.
```

第二行就是**第一道任务要学的那条规则**。它被提前印出来，看着像个泄漏：
第一道任务不必去查（`.membench-fee16` 的第一动作是 `write` 的有 3/8 次，
一次写对 ⇒ 没有失败 ⇒ **没有教训**，教训只落在 5/8 次上）。

**修法试了两条**（一起上）：①隐藏判据的要求只在**失败反馈**里给
（动手之前只公布"存在一项隐藏校验"）；②**第一道任务的 prompt 也不带契约文件**
（`shop/helpers.py` 留在仓里，要查就得查——与第二道任务对称）。

**然后拿 2 reps 试点（`.membench-fee17p`），装置被改坏了：**

| 现象 | 试点（改了装置） | 基线（`.membench-fee16`，没改） |
|---|---|---|
| 第一道任务 | 模型连**读 24 次** `shop/helpers.py`，**一次都没写** → 两次尝试都失败 → `blocked` → **没有教训** | 12 步内写完，8/8 reps 可用 |
| 第二道任务（对照臂） | 写出的 `total()` 连第三个参数都没有（`TypeError`）→ 之后又读了 9 次文件 → **12 步用尽，判红** | 8/8 reps 判绿 |
| 配对样本 | **0** | **8** |

⇒ **拿掉契约，模型不是"失败后修复"，而是"卡住"**：它反复读同一个文件，
把步数预算耗光，任务以 `blocked` 收场。**卡住不产生教训**——
教训只在"失败→被修复"之后才写得出来。
⇒ 这次试点**否掉了这个修法**，装置已回退（守卫测试改成盯住"第一道任务必须带契约文件"，
理由就写在测试的 docstring 里）。

**留下的结论（本轮最有价值的一条）**：

> **教训的产出率由模型行为决定，装置控制不了。**
> 契约在 prompt 里 ⇒ 第一道任务有时一次做对 ⇒ 没有教训（实测 3/8 次）；
> 契约不在 prompt 里 ⇒ 模型卡住 ⇒ 也没有教训（实测 24 次重复读）。
> 两条路都通向"没有教训"，而中间那段（失败→修复）是个**窄窗口**。
> ⇒ 装置能做的只有两件：**把产出率测出来并报出来**
> （`lesson_paired_reps`：只有"教训真进了 prompt"的重复才算"带教训 vs 不带"），
> 以及**别把这个数字藏起来**。

> **纪律**：**"隐藏"不只有一种做法，改法本身也要被试点否掉。**
> 一个"看起来更严格"的改法，如果把装置改到测不出东西，
> 那它比原来的漏洞更糟——因为它让数字**消失**而不是**变红**。

### 19.14 第十四处：发布前的门自己有洞——canary 从没扫过第一道任务

19.13 的修法被试点否掉、装置回退之后，手上有一轮干净数据
（`.membench-fee16`，8 reps，三臂全部有效）可以当基线。
拿它跑 `membench --verify`，门却报了几处"报告与事件流不一致"。
查下来的结论是：**不一致的是门自己，不是数据**——三处，三处都要记下来。

1. **canary 扫描漏掉了第一道任务。**
   报告里那一臂叫 `R1_learn`，可它的日志叫 `events_setup_N.jsonl`
   （`R2_none`/`R2_memory`/`R2_fact` 才是同名）。
   门按报告里的臂名拼文件名 ⇒ 找 `events_R1_learn_N.jsonl` ⇒ **不存在** ⇒
   **第一道任务的日志从来没被扫过**。
   而第一道任务恰恰是模型最可能去找判据的地方——被污染那一轮里，
   模型就是在 `setup_1` 和 `setup_4` 读到了判据源码。
   ⇒ "没有污染"这句话当时**没有根据**。
   修法：报告的臂名 → 日志文件名的映射单列一张表（`membench_verify.LOG_STEMS`），
   守卫测试：`tests/test_heldout.py::LeakDetectionTest::test_the_canary_scans_the_setup_phase_too`。

2. **"L1 失败"这一列有两个定义。**
   报告里的数是**去重后**的（同一个签名只算一次），而事件流里的 `failure` 事件
   也是按去重记的——但**报告是按 outcome 汇总的**，
   监督者重试的那一次尝试不一定落在 `result.outcomes` 里，
   于是两边差 1。门拿这两个数对比 ⇒ 对不上 ⇒ 门要么一直红，要么被人加例外糊弄过去。
   修法：**发布出去的那个数必须与日志记的是同一件事**
   （`NodeOutcome.l1_failures` 在写 `failure` 事件的同一处 +1），
   于是门可以逐行严格核对；对**旧报告**（去重口径、不可复算）门改报 NOTE 而不是不一致
   ——一个永远红的门，和没有门一样危险。

3. **"无效回复"没有列，门却拿它当不一致。**
   模型偶尔交回散文而不是动作（推理模型的思考漏出来），事件流里是 `invalid_action`；
   但逐次明细表里没有这一列 ⇒ 门无从核对 ⇒ 只能报一句"有 N 次无效回复"。
   修法：逐次明细表**加上这一列**，门才能逐行核对。
   （顺带发现：第一道任务（`R1_learn`）那一行压根没把 `invalid` 填进去——
   报告的装配代码漏了这一行。）

4. **门还漏了一个更重要的东西：噪声地板。**
   修好上面三处之后，门是绿的了，但**绿门只保证"数字没抄错"，不保证"效应是真的"**。
   `fee` 族跑完才看出：**同 prompt 的两臂（没有教训可注入的那 3 次重复）
   相差 ±50% 步数 / ±52% tokens**，
   而当时宣称的效应是 -27% / -21% ⇒ **效应比噪声小**。
   修法：门必须**顺手把 A/A 地板算出来**（`NOISE FLOOR` 段）——
   A/A 对照就藏在"注入率"这个设计里，不额外花钱。

> **纪律**：**发布前的门必须先在自己身上跑一遍。**
> 一个只报"通过"的门，和没有门一样危险——
> 因为它让人以为"已经查过了"。

### 19.15 第十五处：被策略打断的 attempt 整块丢失——报告比日志少算了

19.14 修完之后门是绿的，但那是**旧口径**（14 列的报告、去重失败数）。
拿**新口径**重新看同一轮数据，把报告的 L1 列与事件流的 `failure` 事件**逐行对账**，
发现：32 行里**只有一行**对不上——`R2_memory` rep 5。

| | 机器报告 | 事件流（真相） |
|---|---|---|
| 总步数 | 12 | **20**（19 个 action + 1 个被拦下的动作） |
| L1 失败 | 1 | **2** |
| attempt | 1 | **2**（`node_start` 2 次，`node_end` 只有 1 次） |

**机制**（这不是口径差异，是装置缺陷）：

`R2_memory` rep 5 的第二次 attempt 里，模型跑了一条带嵌套命令的命令
（PowerShell 的反引号），风险策略判 `confirm` → 抛 `NeedsApproval`
→ `Executor.run()` 把异常直接抛出去 → scheduler 捕获、置 `blocked`、**`break`**；
而 `result.outcomes.append(outcome)` 在异常分支**之后**（`scheduler.py`），
所以**那个 attempt 的 outcome 从未进账**。
它花掉的 7 个 action、记下的 1 次失败，**只在事件流里**。

⇒ **报告比日志少算了，而且少算得毫无痕迹**：
门当时只比"L1 失败"一列，而那一列在旧报告里是去重口径 ⇒
差异被当成"旧口径不可复算"降级成一条 NOTE ⇒ **看不出来**。

**修法（四处，对所有臂对称，不改模型看到的任何东西）**：

1. **执行器**：被策略/预算打断时，把 attempt 在日志里**收尾**
   （`node_end`，状态 `interrupted`），并把半截 outcome 挂在异常上带走
   （`Executor._interrupt`）。
2. **调度器**：`NeedsApproval` / `DeniedAction` / `BudgetExceeded` 三个分支
   都记下这个半截 outcome —— 但记进 **`result.interrupted`，不进 `result.outcomes`**：
   `outcomes` 的长度是"跑完了的执行器次数"，
   `bench.py` 那个变异测试靠它区分"没跑"与"跑了但一直失败"
   （`is_interrupted()`），把没跑完的算进去会让**每个被打断的臂都被误记成失败尝试**。
   ——这条是守门测试逼出来的：第一次修法直接 append 到 `outcomes`，
   `tests/test_bench_oracle.py::BlockedRunTest` 当场变红。
3. **度量**：`membench._measure` 与 `demo` 把 `outcomes + interrupted` 一起算
   ⇒ 报告的步数与失败数回到与日志同口径。
4. **门**：新增规则——`node_start` 比 `node_end` 多 ⇒
   **点名"被策略打断的 attempt"**，并给出修正后的步数与失败数；
   聚合的 L1 失败数**改用日志的数**（日志才是事情发生的地方）。
   ⇒ 这一列从此**不能被抄错**。

**代价与诚实**：

- 这一轮（`fee16`）**没有重跑**（provider 配额用尽，429）。
  改的是**聚合口径**，不是模型看到的东西 ⇒ 原始产物不变，
  修正后的数字**由脚本从事件流逐格重算**（`python -m planloop.membench_publish rebuild`）：
  32 行里**只有 2 格**变（`R2_memory` rep 5 的总步数 12 → 20、L1 失败 1 → 2），
  聚合的 L1 失败数 1.2 → **1.4**。
  ⇒ 文档里的表**逐格对着重建核验**（`python -m planloop.membench_publish check`），
  手改的一格过不了这一关。
- **本文件的结论一个都没变**（结论只依赖"到验收通过的步数/tokens"和"查表次数"，
  这三列与被打断的 attempt 无关），
  但**上一版文档里那句"聚合值不受影响，逐次口径重算后完全相同"是错的**——
  聚合值确实受了影响。⇒ 又一次印证：**手打的解释也会错**：
  数字要由脚本重算，**"重算之后没变"这句话也得由脚本给**。

> **纪律**：**每一条 NOTE 都必须能说清"为什么"。**
> 说不清原因的 NOTE 等于没报。
> 这次的门原本报的是"旧口径不可复算"（一个技术上的解释），
> 而真正的原因是"有一个 attempt 被整块丢掉了"（一个事实上的解释）。
> ⇒ 门必须能区分**口径差异**（NOTE）与**装置缺陷**（MISMATCH）：
> 前者是数据老，后者是数据错。

## 二十、让「第二次快多少」真的可测：把约定藏起来

第十九节把记忆修活了，但**修活之后测不出价值**：真实模型在这个任务族上一次就做对，
三条臂全绿、结果没差异、记忆只是多花 token。
原因是装置：**旧行为的约定就写在工作区里，模型照抄就行，记忆没有可省的东西。**

于是这一节改了两件事——都是**装置**的改动，没有动执行器的语义。

### 20.1 约定必须不在 prompt 里，否则记忆省不了任何东西

第二道任务要求用 `shop/helpers.py` 的 `pct()` 换算会员折扣，
但它的 **prompt 不带 `shop/helpers.py`**（`Family.r2_context_files`）。
于是想知道契约只能自己打开那个文件——**或者从记忆里直接拿到**。

还有一个细节：仓库里可见的 `tests/test_pricing.py` 断言 `total([100,200],10) == 270`，
配上 `pricing.py` 里的 `subtotal(prices) * pct(discount_pct)`，
模型能推出 **pct(10) == 0.9**——但推不出 **pct(20)**。
所以它还是要读那个文件（或者先写错一次、被仓外判据打回来）。
**能推出一个点，不等于知道一个函数。**

### 20.2 工作量口径不能是「总步数」

执行器要等模型「自己宣布完成」才停，而真实模型做完之后会**反复跑同一套测试**——
那是模型的确认习惯，不是工作量。总步数因此被顶到上限，**总 tokens 也一样**。

新增两个只加信息、不改语义的观测量（`NodeOutcome.steps_to_pass` / `tokens_to_pass`）：
**验收第一次通过时**走到了第几步、花了多少 token。

> 注意：**没有**改「验收一过就停」。改了它，对照臂会在满足窄验收的瞬间停下，
> 于是"仓库还是红的"变成装置制造的假象——而不是模型自己犯的错。
> 这里宁可让模型白跑，也不让装置替它制造结论。

### 20.3 两个信号要分开读

两组的验收集合**故意不同**，混着比就会得出错的结论：

| 组 | 比较 | 为什么可比 |
|---|---|---|
| **成本** | 对照 vs **只有事实** | 事实臂不注入护栏，验收集合与对照臂完全相同 |
| **正确性** | 对照 vs **教训+护栏** | 护栏**就是**把全套测试加进节点验收，差异归因于护栏 |

> 这两条是这一轮学到的第二件事：**装置里"看起来一样的两个臂"，可能验收集合不同。**
> 护栏会改验收项——所以带护栏的臂和对照臂，成本口径根本不可比。

### 20.4 结果：模型**会把记忆当线索，不当结论**

试点数据（1 rep，同一模型同一任务）：

| 臂 | 到验收通过 | 到验收通过的 tokens | L1 失败 | 护栏拦截 |
|---|---|---|---|---|
| 无记忆（对照） | 2.0 步 | 2003 | 1 | 0 |
| 教训+护栏 | 4.0 步 | 4669 | 2 | **1** |
| 只有已验证事实 | 2.0 步 | 2403 | 1 | 0 |

**三臂的第一步都是 `read shop/helpers.py`。**

这说明一件对"做记忆系统"很重要的事：**事实写得很全（函数名、文件、契约、旧行为都在里面），
模型还是要打开源文件核对。**
记忆没有替掉那一步，只是把它变成了"看一眼确认"而不是"读懂"。

⇒ 所以「记忆 = 省掉一次读文件」这个假设**不成立**（至少对这个模型不成立）。
⇒ 记忆在这个任务族上的价值落在**护栏**上：教训臂的护栏当场拦下了一次回归
（对照臂那次没有护栏，同样的问题要到整轮结束才会被仓外判据发现）。

> 这条结论对整个记忆路线是个警告：
> **记忆不能替代读代码，只能替代"试错"。**
> 所以下一个该测的场景是：**那段知识只有试错才能得到**
> （比如上游数据里才有的规则、跑一遍才知道的环境差异），
> 而不是"代码里明明写着、模型读一遍就知道"的东西。

### 20.5 顺带修掉的第三个产品缺陷：一条命令能把整轮挂死

跑到第 4 个 rep 时，进程**停了 15 分钟**：没有输出、没有子进程、CPU 占用为 0。

定位到的原因在 `HostSandbox.run`：模型写了一条**引号不配对**的命令
（`python -c "print(1`）。Windows 上 `cmd.exe` 会**等更多输入**来补上那个引号——
stdin 一直连着，它就一直等。而 `subprocess.run` 的超时也救不了：
杀掉 shell 之后，**孙进程还攥着 stdout 管道**，`communicate()` 就永远不返回。

修法三处：

1. `stdin=subprocess.DEVNULL`——cmd.exe 立刻拿到 EOF，不再等输入；
2. 超时时用 `taskkill /T /F` **杀整棵树**，管道随之关闭；
3. 杀掉之后只再等 5 秒，超时就放弃读管道（不无限等）。

守卫测试见 `tests/test_sandbox_hang.py`（引号不配对不挂死 / 超时会报告 / 正常命令照常）。

> 顺带补了一条**每 rep 落盘**：现在每跑完一个 rep 就把报告写一遍，
> 跑到第 7 个 rep 崩掉不会把前 6 个 rep 的结果一起带走。
> （上一轮就吃了这个亏：rep 4 挂死，前面 3 个 rep 的数据全在内存里，没了。）

### 20.6 补上第三个仪表缺陷：**「没差异」没法归因**

这一节之前的装置只能报**结果**（绿/红、tokens）和**注入**（教训进了几个 prompt）。
但「三臂都没差异」这句话有两种完全不同的含义：

- **记忆没改变行为**（模型照样去核对）；
- **记忆改变了行为，但我们看不见**（模型不核对了，装置却看不出来）。

这两种结论对项目的下一步指向相反：前者说明记忆这条路在真实模型上是死的，
后者说明装置该修。**没有行为数据，这句话就是猜的。**

缺的是数据本身：动作事件（`kind=action`）只记了 **observation**——命令打印了什么、
文件内容是什么——**没有记这个动作碰的是哪个文件 / 哪条命令**。
所以「模型有没有去打开那个藏着约定的文件」这件事，日志里查不到。

修法两处：

1. **事件流补字段**（`planloop/execute.py`）：每个动作事件多带一个 `target`——
   `run` 是命令原文，`read`/`write` 是路径，`write_many` 是排序后的路径列表。
   守卫测试：`tests/test_pipeline.py::ActionTargetTest`。
2. **从事件流回读行为**（`planloop/membench.py::analyze_events`）：
   统计动作数、读/跑/写各多少次、**第一步是什么**，
   以及 **「动了隐藏约定」次数**——动作的 observation 里出现了隐藏约定的源码，
   就说明模型又去打开它了（标记由任务族给出：`Family.hidden_markers`）。
   报告的逐臂表因此多了两列，结论段多一条**行为口径**。
   守卫测试：`tests/test_membench.py::EventAnalysisTest`。

另外给 CLI 加了 `--analyze`：不用重跑，直接从跑完的目录里把行为读回来——

```bash
python -m planloop membench --analyze --real --dir .membench-real11
```

> 为什么值得单独记一笔：**这是第三次在同一个装置上找到"仪表自己有问题"**。
> 前两次是①报告里的污染检查是默认值渲染出来的（§十七.1）、
> ②「跑了但失败」和「根本没跑完」被算成同一件事（§十七.3）。
> 第三次是这次：**装置能证明"结果没差异"，却证明不了"行为有没有差异"**。
> 三次都指向同一件事——
> **一个只会报结果的装置，会把"我什么都没测到"报成"我测了，没有"。**

## 二十一、装置的第三个缺陷：**知识是可选的，所以测不出记忆**

第二十节把约定藏到了 prompt 之外，装置看起来对了。但 8 次重复跑完，
数字摆出来是这样（对照臂 vs 事实臂）：

- 三臂**全部为绿**——没有记忆也没有记忆**一样对**；
- 隐藏约定被打开的次数，对照臂 4~5 次，事实臂 1~4 次——**有差异，但很小**；
- 到验收通过的 tokens，事实臂反而更高。

到这里为止，结论应该是"记忆没测出收益"。但**这个结论本身不可信**，
因为装置还有一个更根本的问题没被发现。

### 21.1 那个约定，是**猜得出来**的

`contract` 任务族里，可见测试钉的是：

```python
self.assertEqual(total([100, 200], 10), 270)      # 300 * 0.9
```

于是模型只要推出 **pct(10) == 0.9**，就顺手推出 **pct(20) == 0.8**——
因为 `0.9 = 1 - 10/100`、`0.8 = 1 - 20/100`，**"打折后的剩余比例"就是那个显然的公式**。

而仓外判据要的正是 `300 * 0.9 * 0.8 == 216`。
**一个从不打开 `shop/helpers.py`、只按显然公式写代码的模型，可以拿满分。**

这就把第二十节的前提推翻了：**约定虽然不在 prompt 里，但它是"可推导"的，
所以它不是"必须知道的知识"，只是"可以去核对的说法"。**

于是"记忆替掉一次核对"这个命题从一开始就没有测到东西：
对照臂那次核对是**自愿的**（不核对也能过），省掉它省不下任何东西。

> 这是本项目第三次栽在同一类问题上：**装置自己把待测的知识做成了可选的**。
> §十七两次是"仪表把没测到的东西报成测到了"，这次是"待测项被做成了可有可无"。

### 21.2 修法：让知识**必须**被知道

新任务族 `fee`（`planloop/membench.py::FEE_FAMILY`）改两处，都是装置侧：

1. **契约不再是显然公式**：平台费**按折扣档位**取值（0%→0.00、10%→0.02、20%→0.05），
   所以 `pct(10) == 0.88` **推不出** `pct(20) == 0.75`。
   可见测试只钉 10% 那一行；20% 那一行**只有读文件才知道**。
2. **判据不泄题**：仓外判据的断言消息是固定字符串，
   **不打印期望值**——否则失败反馈会直接把答案送给对照臂
   （`contract` 族的判据消息里就写着 `pct(10) == 0.9`，那正是泄漏）。

守卫测试在 `tests/test_membench.py::FeeFamilyTest`：
可见测试不含 198（会员那一行的答案）、判据消息里没有任何小数、
事实给的是**规则**（档位表）而不是答案。

### 21.3 于是这次测的才是真问题

| | `contract` 族（v2） | `fee` 族（v3） |
|---|---|---|
| 契约能猜吗 | **能**（`1 - p/100`） | **不能**（档位表） |
| 不查资料能过吗 | **能** | **不能** |
| 那次"核对" | 自愿的 | **必需的** |
| 记忆替掉的是 | 一次可选的确认 | **一次必需的查表** |

这样才问出真问题：**模型愿不愿意相信记忆里的知识，而不自己去查？**
"查"从"确认"变成"必须"之后，记忆才有东西可以省。

> 这一节的教训比这一节的数据更重要：
> **一个测不出差异的装置，先要问"差异本来应该出现在哪"，再问"模型为什么没差异"。**
> 这一轮的回答是：差异本该出现在成本上，但契约被做成了可猜的，
> 于是"没有差异"其实等于"没有可比的东西"。
> **先证伪装置，再谈模型。**

### 21.4 试点：新装置真的成立了吗（1 rep）

`fee` 族跑了一次试点（真实模型，同一模型同一任务）：

| 臂 | 外部判定 | 到验收通过：步数 | 到验收通过：tokens | 隐藏约定被打开 |
|---|---|---|---|---|
| 无记忆（对照） | **绿** | 2.0 | 2011 | 3 次 |
| 教训+护栏 | **绿** | 3.0 | 3776 | **7 次** |
| 只有已验证事实 | **绿** | 2.0 | 2314 | 5 次 |

三件事可以确认：

1. **装置这一侧成立**：三臂都做对了——说明"契约不可猜"没有把任务变成做不出来，
   而对照臂要花 2 步（`contract` 族只要 1~2 步但那是不需要知识的），
   它确实得**找到档位表**才能写对。
2. **教训真的进了 prompt**（12/14）——19.6 修完之后，兜底模板不再是默认命运。
3. **但记忆臂查得更多**（3 → 7 → 5 次），成本也更高。

第 3 条**不能当结论**（n=1），但它和 `contract` 族 8 reps 的方向一致：
**注入知识没有减少查表，反而增加了查表。**

> 这次试点还顺带暴露了一个**必须先修的东西**：教训生成器只拿到
> "wrote 239 chars to shop/helpers.py"这样一行摘要，
> 于是它**编了一个原因**（说修复是"每个档位都用 1 - p/100"，
> 而模型实际写的是带档位表的那一版）。
> 一条编错的教训会被**带着匹配的触发条件**灌进下一道任务——
> 比没有教训更糟。修法见 §十九.7。

### 21.5 把"反证"从一族推广到**每一个族**（2026-11-12）

`contract` 族那一轮白跑，根因是**没人检查"知识是不是必需的"**——
反证测试（"把显然公式写进仓库，仓外判据必须判红"）当时只写在 `fee` 族名下，
所以下一个族上线时，没人被要求做同样的检查。

⇒ 现在每个族都必须**自己声明**：

- `Family.guessable_solution`：**模型能猜到的那个解**（文件 → 内容）；
- `Family.shortcut_rejected`：仓外判据**必须拒绝**它——
  `fee` 族是 `True`（档位表猜不出来），
  `contract` 族是 `False`（可见测试钉了 10% 那一行，显然公式把 20% 那一行也猜对了）；
