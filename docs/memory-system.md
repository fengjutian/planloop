# 记忆系统

> 状态：**M1 已实现**（SQLite + FTS5 + 向量、公有/私有分库、写决策与变更历史、双时态、可执行 procedure、AGENTS.md 导出）。
> 本篇讲完整的正向记忆；负向记忆（错误与护栏）见 [错误记忆](memory.md)；与市面方案的对比见 [调研](market-scan.md)。

## 一、五类记忆

| 类型 | 内容 | 例子 | 生命周期 |
|---|---|---|---|
| `fact` | 仓库的稳定知识 | `test_command: python -m unittest ...` | 90 天 |
| `procedure` | 怎么做某类事，**可执行** | `run_tests` → `python -m unittest ...` | 180 天 |
| `decision` | 为什么这么选、否掉了什么 | `选 JSONL 不选 SQLite，因为要 append-only` | 永久 |
| `episode` | 一次运行发生了什么 | `run-1731: [succeeded] 修折扣 / 4 节点` | 30 天 |
| `lesson` | 犯过的错与护栏 | 见 `docs/memory.md` | 长，会衰减 |

## 二、四条既定决策

| 决策 | 选择 | 原因 |
|---|---|---|
| 存储 | SQLite + 向量（float32 BLOB） | 单文件、可查询、支持 TTL 与全文检索 |
| 写入权限 | 接受模型自动写入，但**必须带证据** | 无证据的条目封顶 confidence 0.35 |
| 作用域 | 按仓库隔离（`repo:<sha1>`） | 跨项目污染是最常见的崩坏方式 |
| 可见性 | 公有 / 私有**两个物理库文件** | 约定会被漏写的 WHERE 破坏，文件不会 |

```
<repo>/.planloop/memory/public.db    ← 可提交，`mem export` 生成 AGENTS.md
<repo>/.planloop/memory/private.db   ← .gitignore，永不外传
```

## 三、写决策与变更历史

不是"存下来"，而是"决定怎么存"：

| 操作 | 触发 | 记录 |
|---|---|---|
| `ADD` | 该 key 从未存在 | 新值 + 理由 |
| `UPDATE` | 值或 exec 变了 | 旧值 → 新值 + 理由 |
| `NOOP` | 完全一致 | 只更新 updated_at，置信度取 max |
| `DELETE` | 显式遗忘 / 失效 | 关闭有效期 + 理由 |

每次写入都落一行 `memory_history(op, old_value, new_value, confidence, reason, at)`。

```bash
$ planloop mem history m_9c81
NOOP    2026-11-09 21:21 conf=0.80 unchanged
UPDATE  2026-11-09 21:24 conf=0.80 changed my mind
        旧: python -m unittest discover -s tests
        新: python -m unittest discover -s tests -t .
```

**这就是"记忆"和"审计"的交汇点**：能回答"这条事实什么时候、为什么变的"。

## 四、双时态：过期不是删除

```
valid_from ──────────── valid_to(null = 仍然有效)
      └── 事实在某段时间内成立，而不是"存了就一直对"
created_at / updated_at  ── 我们是何时记录它的
```

- `valid_to` 到了 → 检索直接排除（而不是靠状态标记）；
- `mem verify` 重跑证据失败 → `stale` + 扣 0.4 置信度；
- `mem forget` → 设 `valid_to=now` + `status=archived`，历史保留。

## 五、可执行的 procedure

文字流程记不住也用不上。procedure 带 `exec_spec`：

```bash
planloop mem add --kind procedure --key run_tests \
  --value "run the unit test suite" \
  --exec "python -m unittest discover -s tests -t . -q"

$ planloop mem run run_tests
Ran 61 tests ... OK
```

成功 → confidence +0.05；失败 → −0.2。**procedure 的可信度由它跑得通不通决定**，不由描述写得好不好决定。

## 六、检索：混合打分，可解释

```
score = 0.45·cosine + 0.35·bm25 + 0.12·confidence + 0.08·usage + 0.12·key_hit
```

默认 embedder 是 384 维**特征哈希**，没有语义理解能力，带来的是模糊词法匹配。只有配置 `PLANLOOP_EMBED_MODEL` 时 cosine 才是语义的。所以文档里不写"语义检索"。

## 七、导出为 AGENTS.md（互操作 + 三道闸）

```bash
planloop mem export --out AGENTS.md --yes
```

```markdown
<!-- generated by planloop from public.db: 2 entries, tiers A,B; edits will be overwritten -->
## Project memory (repo:e1ab10a5084a)

> Generated from verified project memory. Treat as reference, re-check before acting.

### Facts
- **test_command**: python -m unittest discover -s tests -t .

### Procedures
- **run_tests**: run the unit test suite - `python -m unittest discover -s tests -t . -q`
```

别的工具不认识 SQLite，但认识 AGENTS.md。

### 为什么导出要设闸

导出物会被下一个 agent 当作**指令**读取。于是存在一条完整链路：

```
模型写记忆 → 判重/验证 → public.db → mem export → AGENTS.md → 下一个 agent 的指令
```

这与 [MemPoison](https://neurips.cc/virtual/2026/loc/sydney/poster/139557) 描述的持久化污染是同一条路径，只是我们的出口更直接。所以设三道闸：

| 闸 | 规则 | 拒绝示例 |
|---|---|---|
| **证据分级过滤** | 默认只导出 A（command）/ B（file）级；C（人工背书）与 D（无证据）必须显式请求 | `--tiers A,B,C` → `refusing: tier C ...` |
| **覆盖审批** | 目标文件已存在时必须 `--yes` | `AGENTS.md exists; pass --yes to overwrite` |
| **生成物标记** | 文件头写明来源、条目数、档位；正文首行声明"仅作参考，执行前复核" | — |

实测：

```bash
$ planloop mem export --out AGENTS.md          # exit 2
AGENTS.md exists; pass --yes to overwrite

$ planloop mem export --tiers A,B,C            # exit 2
refusing: tier(s) C are not machine-verified...
```

**一个真实观察**：导出后，这个文件会被 agent 运行时自动加载为工作区指令。所以"记忆污染"和"提示注入"在这套架构里是同一个问题——闸必须设在导出这一侧，而不是指望下游去分辨。

## 八、证据规则

| 类型 | 形状 | 验证 |
|---|---|---|
| `command` | `{"type":"command","spec":"python -V","exit":0}` | 重跑，比对退出码 |
| `file` | `{"type":"file","path":"shop/pricing.py"}` | 存在性（禁止逃出仓库） |
| `manual` | `{"type":"manual"}` | 人工背书，置信度上限 0.6 |

`mem verify` 重跑所有证据，失败的降为 `stale`。

## 十、命令

```bash
planloop mem add --kind fact --key test_command --value "..." --evidence-command "python -V"
planloop mem add --kind procedure --key run_tests --value "..." --exec "..."
planloop mem search "how do I run the tests"
planloop mem list | stats | verify
planloop mem history <id>          # ADD/UPDATE/NOOP/DELETE 的完整轨迹
planloop mem run <procedure-key>   # 执行 procedure
planloop mem export --out AGENTS.md
planloop mem promote <id>          # 私有 → 公有
planloop mem forget <id>           # 关闭有效期并归档
```

## 十一、怎么证明它有用

唯一有说服力的指标：**同类任务第二次比第一次少走多少步。**

| 指标 | 目标 |
|---|---|
| 探索步数下降（第 2 次 vs 第 1 次） | ≥30% |
| 记忆占上下文比例 | <15% |
| 陈旧率（stale + refuted / active） | <10% |
| 误用率 | <10% |

## 十三、已知限制

1. 默认 embedder 无语义能力，同义改写召回差。
2. FTS5 的 `unicode61` 对中文按字切分，中文检索质量一般。
3. 没有冲突检测：两条矛盾的 fact 会并存，靠 confidence 排序掩盖。
4. 全表载入算 cosine，规模大了会慢。
5. `mem promote` 没有审批环节，私有/公有边界靠人。
6. `NOOP` 不记录值的变化，只记录"没变"——如果同一 key 被反复写成相同值，历史会变长但没有信息量。
