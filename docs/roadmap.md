## P4 模型分档路由（已完成）

**为什么排最后**：长任务里省钱不是主要矛盾；且需要 P0 的 trace 才能校准 `p_w`。

- [x] `routing.py`：cheap / standard / strong / verify，档位缺失时按 standard → cheap → strong 回落
- [x] 失败升级（attempt>0 → strong）+ 记忆命中抬档 + 决策写事件日志（`route`）
- [x] 加权成本 `cost_units = Σ tokens × weight`
- [x] 验证器隔离：`verify` 档与执行档实例重合时返回 `None`
- [x] 三组对照实验（`examples/routing_demo.py`），两种工作量

**验收结果**：

| 工作量 | 全 cheap | 全 strong | 路由 |
|---|---|---|---|
| 1 易 + 1 难 | 失败，cost 174 | 成功，2313 | 成功，**2151**（省 7%） |
| 4 易 + 1 难 | 失败，413 | 成功，5895 | 成功，**2390**（省 59%） |

未达"≤ all-strong × 0.6"的场景（1 易 + 1 难，省 7%）是真实结论，不是缺陷：**路由的收益与简单任务占比成正比**。成本为权重假设，接真实模型需按真实单价重算。

详见 [模型分档路由](routing.md)。

## P7 对照基准（已完成）

**要回答**：同样的模型、同样的预算下，"验证 + 重试"是否比"多发几次投票"划算。

- [x] `bench.py`：三个真实任务（修 bug / 加功能 / 重命名）、B0/B1/B2 三种配置
- [x] 独立 oracle（跑测试）判定成功，不由被测配置自评
- [x] 固定随机源，结果可复现
- [x] `planloop bench --reps/--seed/--p-correct/--out`

**脚本模型结果**（p=0.6，reps=10，seed=7）——**只证明 harness 正确，不预测真实模型表现**：

| config | 成功率 | 平均 tokens |
|---|---|---|
| B0 | 63% | 134 |
| B1 | 73% | 668 |
| B2 | 80% | 1246 |

**真实模型结果**（MiniMax-M3.1-Flash，真实 API，仓外 held-out 判据，2 道"模型自己宣布完成"的题）：

| config | 成功率 | 平均 tokens |
|---|---|---|
| B0 单发（盲） | 0/10 | 14445 |
| B1 三次投票（盲） | 0/9 | 39576 |
| B2 验证 + 带诊断重试 | 9/9 | 8322 |

Fisher 单侧：B2 vs B0 `p=1.1e-5`、vs B1 `p=2.1e-5`。

> **验收门（已修订）**：脚本模型的百分比**不能**当验收门——它对真实模型没有预测力（脚本 B0 63% vs 真实 B0 0%）。
> 门只能是：**真实模型 + 工作区外的独立判据 + 统计显著性**，且不显著时允许弃权。
> 四臂消融进一步定位到收益来源是"失败反馈带诊断"（B2D 0/5 vs B2 6/6，`p=2.2e-3`）。
> 详见 [对照基准](bench.md)、[四臂消融](bench-ablation2.md)、[项目主张分析](analysis.md)。

详见 [对照基准](bench.md)。

## P8 记忆深化

**现状（2026-11-11，`fee` 族第四版装置，8 reps 全部有效、canary 零污染）**：
记忆的**行为**收益测到了——**已验证事实让模型少查 50% 的档位表**
（72 → 36 次，8 次里 7 次更少，唯一在 A/A 噪声地板之上的效应）；
**成本**收益测不出来（-27% 步数 / -21% tokens，落在 ±48%/±52% 的地板之内）；
**模型写的教训**这轮**没测出收益**（5/8 次真注入，但没替掉任何核对：查表 72 → 92）。
⇒ 下一步三件事，**顺序不能反**：①**先降噪**（提高重复次数，或换效应量更大的任务族）；
②**再改教训的保真度**（让它携带可复用的知识，而不是契约转述）；
③**最后才谈合并/取舍**（"事实臂要不要也配一条护栏"）。
⇒ 在①完成之前，**不合并、不加功能**。

- [ ] 记忆作用域：按仓库隔离 + 全局流程层
- [ ] TTL 与容量上限
- [ ] 冲突检测（同一触发条件下两条相反的 fix）
- [ ] `planloop memory audit`：人可审阅、可撤销

**验收门**：注入一条错误 lesson，系统能通过误杀检测把它降到 `refuted`。

**追加门（价值门，2026-11 新增）**：记忆系统不能只证明"机制能工作"，还要证明"它值那些代码"。
度量装置已就位（`python -m planloop membench`，[记忆值不值](memory-value.md)）：
第二次同类任务里，教训+护栏与已验证事实**两条路径收益重合**——说明是**合并/取舍**的问题，
不是继续加功能的问题。任何新的记忆能力，必须在这套装置上**不劣于**现有基线，否则不加。

**追加门（噪声地板门，2026-11-11 新增）**：**报效应之前，先报同 prompt 的 A/A 噪声地板。**
`fee` 族 8 reps 里，教训臂在**没有教训可注入**的那些重复里与对照臂
**prompt 完全相同**（记忆块是空的）⇒ 两臂的差**就是模型自己的方差**。
实测（`.membench-fee16`）：同一 prompt 下两臂相差 **48% 步数 / 52% tokens / 21% 查表**。
⇒ 而"事实臂省 27% 步数、21% tokens"**落在噪声地板之内**，不能当收益报；
只有**行为口径**（查表次数 -50%）站得住。
⇒ 装置必须把噪声地板一起算出来（`membench --verify` 的 `NOISE FLOOR` 段），
**效应小于地板的一律报成"测不出来"**。
（被撤回的那一轮 `.membench-fee9` 同样量到了地板：-33% 步数 / -29% tokens——
它当年的"-45% tokens"其实只是**勉强**在地板之上。）
⇒ 这条门是免费的：A/A 对照就藏在设计里，**前提是你把"这一轮到底有没有注入"报出来**。

**追加门（额度门，2026-11-11 新增）**：**外部额度是实验设计的一部分**。
provider 的配额用尽返回 429（"已达到 Token Plan 用量上限"），
现象是**立刻失败**（0.3s）而不是挂死——一轮 8 reps 里可以有 7 次是这种死法，
剩下的配对样本就只剩 1 次。
⇒ 装置必须把"provider 失败"和"模型做错"分开标记，
报告必须写明**这一轮实际损失了多少重复**（而不是只报有效样本）。

**追加门（真实模型门，2026-11-11 新增）**：脚本模型上的机制有效 ≠ 真实模型上有效。
换成真实模型后第一件事是**发现十四处一测就死的环节**（教训生成预算被思考吃光、
带 `error_patterns`/`commands` 的触发条件永远检索不到、模型写的护栏 `must`
不可解析时判据恒为真、非法正则炸掉检索、`goals` 写成字符串被逐字符拆成通配，
以及模型写的 `shop/**/*.py` 触发条件永远匹配不上，见 [bench.md](bench.md) §十九）。
所以记忆类的任何结论现在必须满足三条：

1. 用**真实模型**跑（`--real`），并报**注入命中率**（`带教训的 prompt` / `带事实的 prompt`）；
2. 装置必须能证明"记忆真的进了 prompt"，否则测的是"库里有东西"；
3. 任何新能力要在**真实模型基线**上不劣，而不是在脚本模型基线上。

**追加门（工作量口径门，2026-11-11 新增）**：总步数不是成本口径。
执行器要等模型「自己宣布完成」才停，而真实模型做完之后会反复跑同一套测试——
总步数、总 tokens 都会被顶满。装置必须改报**「到验收通过的步数 / tokens」**
（`NodeOutcome.steps_to_pass` / `tokens_to_pass`）。

**追加门（行为口径门，2026-11-11 新增）**：只报结果不报行为，装置分不清
「记忆没改变行为」和「记忆改变了但装置看不见」。装置必须能从**事件流**回读
「模型有没有去查那个隐藏约定」（`planloop/membench.py::analyze_events`，
CLI `membench --analyze`），
否则"没差异"这句话就是猜的。

**追加门（装置自检门，2026-11-11 新增）**：装置自己必须先被证伪。
上一轮"记忆没测出收益"的结论有一半是装置的毛病——
`contract` 族的契约**猜得出来**（可见测试钉住 270，模型推出 0.9 就推出 0.8），
于是那次核对是自愿的，记忆压根没东西可省。
新增任务族必须先过一条**反证测试**：
「把显然公式写进仓库，仓外判据必须判它不通过」——
否则装置测的还是可猜的东西。

**追加门（注入率门，2026-11-11 新增）**：效果必须和**注入率**一起报。
上一轮教训臂"没测到收益"，回读事件流才发现：**5 次配对重复里它只带着教训跑了 2 次**
（模型写的 `shop/**/*.py` 触发条件永远匹配不上，[bench.md](bench.md) §十九.9）。
注入率低的时候，"没差异"分不清是"记忆没用"还是"**记忆根本没进去**"。
⇒ 装置必须报**每个臂的注入率**，注入率不够的臂**不算一次有效对比**。

**追加门（判据可达性门，2026-11-11 新增）**：**判据必须自己证明自己没被读到**。
上一轮已发布的 `fee` 族数字被撤回：判据虽然"在仓外"，但
**`run` 走 shell**（`cd /d ... && type ...oracle\r1_oracle_1.py`），
模型读到了判据源码——**答案就在里面**；而失败反馈的 traceback 还会把答案打印出来。
⇒ "仓外"不等于"读不到"。
⇒ 判据改成**从 stdin 喂给 python**（磁盘上根本没有它，从 stdin 来的程序
traceback 里也没有源码行）；每次重复的判据带唯一 canary，
跑完扫事件流和工作区，**命中即作废该次重复**。
⇒ **这一门是"发布前"的**：数字要先过 `membench --verify`，它会同时报被污染的重复。
一个会污染结果的装置缺陷，比一次没测出来更贵——它污染的是已经发布的数字。

**追加门（隐藏彻底门，2026-11-11 新增，**试过修、改坏了、已回退**）**：
藏住答案还不够，答案的说明书也不该提前给——但**这一版修法被试点否掉了**：
把契约从验收文本里拿走、并把契约文件从第一道任务的 prompt 里拿走之后，
模型**连读 24 次**同一个文件、一次都不写，第一道任务 `blocked`、没有教训，
第二道任务也判红（配对样本 0）。
⇒ **教训的产出率由模型行为决定，装置控制不了**。
⇒ 装置能做的只有：**把产出率测出来并报出来**
（`lesson_paired_reps`——只有"教训真进了 prompt"的重复才算"带教训 vs 不带"），
以及**别把这个数字藏起来**。
⇒ 纪律：**改法本身也要被试点否掉**——一个"看起来更严格"的改法，
如果把装置改到测不出东西，它比原来的漏洞更糟。

**追加门（噪声地板门，2026-11-11 新增）**：**报效应之前，先报同 prompt 的 A/A 噪声地板。**
`fee` 族 8 reps 里，教训臂在**没有教训可注入**的那些重复里与对照臂
**prompt 完全相同**（记忆块是空的）⇒ 两臂的差**就是模型自己的方差**。
实测（`.membench-fee16`）：同一 prompt 下两臂相差 **48% 步数 / 52% tokens / 21% 查表**。
⇒ 而"事实臂省 27% 步数、21% tokens"**落在噪声地板之内**，不能当收益报；
只有**行为口径**（查表次数 -50%）站得住。
⇒ 装置必须把噪声地板一起算出来（`membench --verify` 的 `NOISE FLOOR` 段），
**效应小于地板的一律报成"测不出来"**。
（被撤回的那一轮 `.membench-fee9` 同样量到了地板：-33% 步数 / -29% tokens——
它当年的"-45% tokens"其实只是**勉强**在地板之上。）
⇒ 这条门是免费的：A/A 对照就藏在设计里，**前提是你把"这一轮到底有没有注入"报出来**。

**追加门（门自检门，2026-11-11 新增）**：**发布前的门必须先在自己身上跑一遍。**
上一轮的门漏掉了**第一道任务**的日志（报告里叫 `R1_learn`，日志叫 `events_setup_N`）
⇒ canary 从没扫过模型最可能去找判据的那一段 ⇒ "没有污染"当时没有根据。
⇒ 门必须覆盖**每一段**日志；门比对的每个数都必须与原始产物**同口径**
（"L1 失败"在报告里是去重口径、在日志里是逐次口径 ⇒ 永远对不上）。
⇒ 一个只报"通过"的门，和没有门一样危险。

> 现状（2026-11-11，真实模型 M3.1-Flash，`fee` 族 8 reps，三臂都有效的配对样本 5 次）：
> **v2（`contract` 族）的"没测到收益"已被证伪为装置缺陷**——契约猜得出来，
> 知识从来不是必需的，那次核对是自愿的。**"没测到"不等于"没有"。**
> v3（`fee` 族，平台费按档位取值，知识必需，有反证测试）才测到东西：
> - 成本口径（对照 vs 事实）：到验收通过 **3.0 → 1.6 步（-47%）、3579 → 1975 tokens（-45%）**
> - 行为口径（隐藏约定被打开）：**25 → 17 次（-32%）**，5 次里 4 次更少
> - 正确性：绿 对照 **4/5**、教训臂 **5/5**、事实臂 **3/5**
>
> ⇒ **已验证事实有真实价值**，第一次测到。**但省下的那次核对正是没发现回归的那次核对**：
> 3 次红全部是「节点验收过了、仓外最终判据判红」。
> ⚠️ **教训臂这轮没测到**：5 次配对重复里它只带着教训跑了 **2 次**
> （第九处失效：模型写的 `shop/**/*.py` 触发条件永远匹配不上），
> 所以"教训有没有收益"**必须重测才能回答**。
>
> ⇒ 下一步**两件事，顺序不能反**：①**重测教训臂**（失效已修）；
> ②再问「要不要给事实臂也配一条护栏」。
> **仍不合并、不加功能**——先把正确性那侧补上，再重测。

## P9 动态计划修订（已接受，待实现）

**目标**：把当前“失败后选择重试/停止”的局部重规划，升级为可追溯、可验证、可回滚的计划版本系统。计划修订不得原地覆盖当前计划。

### v1 范围

- [ ] `PlanRevision`：版本号、父版本、触发原因、操作列表、预算变化、计划指纹
- [ ] 五种结构化操作：`add`、`replace`、`split`、`cancel`、`add_dependency`
- [ ] 每次修订生成机器可读 diff，并保存完整快照到 `plans/vN.json`
- [ ] 修订写入 append-only 事件日志，审计报告可回答“哪次修订改了什么、为什么改”
- [ ] 从变更节点计算下游依赖闭包，只重置受影响节点
- [ ] 已完成且未受影响的节点、验收证据和产物继续复用
- [ ] 修订后重新执行 compile 校验：循环、悬空依赖、接口、验收、里程碑、成本与不可逆闸门
- [ ] 对比修订前后的估算成本和剩余预算；超预算时拒绝应用
- [ ] 用计划指纹、重复操作检测和硬次数上限阻止 A→B→A 式震荡

### 暂不纳入 v1

- 自动合并节点
- 动态创建或重组里程碑
- 多个候选计划的并行搜索
- 无人值守的全局计划替换

这些能力依赖更成熟的冲突处理和真实任务评测，避免第一版同时扩大状态空间和安全边界。

### 验收门

构造 `T1 → T2 → T3`：T2 因接口假设错误被拆成 `ProbeAPI → T2a → T2b`。应用修订后必须满足：

1. T1 保持完成且不重复执行；
2. 新节点及 T3 被标记为待执行，依赖顺序正确；
3. `plans/v1.json`、`plans/v2.json` 和结构化 diff 均可读取；
4. 审计日志包含修订原因、影响集和预算增量；
5. 引入循环、预算超限或重复计划指纹的修订被拒绝，当前计划保持不变。

详见 [审计与回滚](audit-rollback.md#七动态计划修订p9)。

## 战略扩展方向

后续不再以“平铺模块”为目标，而围绕三个结果推进：

1. **提高真实成功率**：证明机制在真实任务中有效，而不只是在脚本模型和演示任务中成立；
2. **扩大可用任务范围**：支持动态计划、增量验收、并行执行及更丰富的验收对象；
3. **形成可靠工程平台**：让运行可观察、可复现、可治理，并逐步具备插件化和远程执行能力。

以下顺序表示产品优先级，不表示所有项目应同时开工。每个方向必须先定义独立验收门，再进入实现。

### 1. 真实任务评测平台（最高优先级）

**目的**：从“设计合理”走向“效果可证明”。

- 从真实 GitHub issue 或经过人工审核的真实缺陷生成任务集；
- 固定仓库 revision、运行环境、依赖和独立验收命令；
- 记录成功率、耗时、token、工具调用数、回滚次数与人工介入次数；
- 分开报告“测试通过”“需求完成”“没有引入回归”；
- 对比单 Agent、PlanLoop、PlanLoop + Memory、PlanLoop + Milestone；
- 重复运行并报告方差、置信区间和失败分布；
- 保存完整失败轨迹，并对失败原因做聚类。

目标管线：

```text
task → isolated workspace → N repeated runs → independent oracle
     → trace dataset → aggregate report
```

**验收门**：至少 10 个真实任务、每种配置重复运行，报告可复现且成功结论完全由独立 oracle 给出。

**追加门（判据本身要过测）**：每个真实任务要拆出「正确版 + 注入缺陷版」，
报告**判据召回率**与**漏检分类**；判据抓不到的缺陷要写进报告，而不是换个任务绕过去。
方法与样板见 [判据召回率](fault-recall.md)（`python -m planloop faults`）。

### 2. 动态计划修订

当前失败处理主要在重试、局部修复和停止之间选择。下一阶段升级为不可变计划版本、结构化 diff、影响集重跑、预算差异和防震荡机制。

完整 v1 范围及验收场景见 [P9 动态计划修订](#p9-动态计划修订已接受待实现) 和 [审计与回滚](audit-rollback.md#七动态计划修订p9)。

### 3. 并行执行与工作区隔离

- 独立节点在 Git worktree 或临时副本中执行；
- 节点声明读集、写集和文件所有权；
- 仅并行调度无依赖且写集不冲突的节点；
- 按依赖顺序合并结果；
- 合并冲突生成专门的 reconciliation 节点；
- 并发任务获得独立 token、工具调用和时间预算。

示例契约：

```text
T1 owns: src/auth/**
T2 owns: tests/auth/**
T3 reads: src/auth/**, writes: docs/**
```

**前置条件**：先完成文件所有权与冲突语义；不以简单线程池作为并行实现。

### 4. 增量验证

- 根据改动文件选择相关测试；
- 基于 import/call graph 计算影响范围；
- 节点结束运行局部测试，里程碑运行受影响测试集，最终运行全量回归；
- 局部验证失败或风险升高时自动扩大验证范围；
- 对历史漏检建立“必须全量测试”的风险规则。

验证升级路径：

```text
changed test → package tests → affected integration tests → full suite
```

**验收门**：在不降低已知缺陷召回率的前提下，显著降低真实任务的平均验证时间。

### 5. 声明式验收语言

在现有 criterion 上增加：

- HTTP 请求与响应、数据库查询、JSON Schema / JSONPath / XPath；
- 性能阈值、文件差异约束、DOM 与截图验收；
- “不得改变”的负向约束；
- AND、OR、至少 N 项通过等组合条件；
- 验收前置条件和清理动作。

验收 DSL 必须保持可序列化、可审计，并明确每种检查的证据等级、权限和确定性。

### 6. 风险驱动调度

风险信号包括修改文件数、敏感区域、历史变更频率、测试覆盖、可逆性、相似任务成功率和验收器召回率。风险评分用于决定：

- 模型档位和是否追加 probe；
- 是否增加人工里程碑；
- 是否强制使用隔离沙箱；
- 局部或全量验证；
- 是否允许自动合并。

风险决策及其输入必须写入事件日志，不能成为不可解释的隐藏分数。

### 7. 面向运行轨迹的可观测性

- 运行时间线和 DAG 实时状态；
- token、成本与延迟瀑布；
- 节点上下文来源、计划版本对比和验收证据浏览；
- “为什么停止”“为什么升级模型”的解释；
- OpenTelemetry 导出和失败轨迹重放。

**体验目标**：操作者能在一分钟内回答“做了什么、为什么做、证据是什么、现在卡在哪里”。

### 8. 可复现执行与缓存

为节点建立内容寻址签名：

```text
hash(
  node spec
  + dependency artifacts
  + repository revision
  + model/prompt version
  + toolchain version
)
```

签名相同且证据仍有效时复用产物和验证结果；签名相同但结果不同则记录非确定性。跨运行缓存必须验证作用域、权限、产物哈希和证据有效期。

### 9. 记忆系统治理

- 仓库、语言、框架和版本作用域；
- 冲突检测、时态查询、自动降权与过期；
- 区分事实、经验、策略和临时观察；
- 解释命中原因，开展记忆注入 A/B 实验；
- 防止仓库内容通过记忆成为持久指令；
- 记录每条记忆的应用次数、阻止失败数、误杀数和额外成本。

记忆是否保留由实际收益和证据决定，而不是由写入次数决定。该方向与 [P8 记忆深化](#p8-记忆深化) 合并推进。

### 10. 插件化能力

核心接口稳定后，再为 Planner、Executor、Verifier、Sandbox、Memory、Model Router、Policy、Artifact Store 和 Event Sink 定义插件协议。插件必须声明：

- 输入输出 schema 与兼容版本；
- 所需权限；
- 确定性、幂等性和可重试性；
- 成本估算与资源需求。

接口未稳定前不承诺第三方兼容，避免过早固化错误抽象。

### 11. 分布式与远程执行

后期可增加远程 worker、工具链镜像选择、节点租约与心跳、失联后的幂等重试、产物上传与签名、多租户配额，以及 E2B、Kubernetes、MicroVM 后端。

该方向属于平台化阶段，依赖节点幂等、内容寻址缓存和可靠工作区隔离。

### 12. 软件供应链安全

- 锁定工具、依赖和执行镜像版本；
- 依赖安装网络白名单与凭据代理；
- 产物哈希、签名和 SBOM；
- 审批记录防篡改；
- 仓库内容 prompt injection 检测；
- 对外发送前的数据分类和出站策略。

安全能力应随执行权限同步增强；在强隔离和出站控制完成前，不把系统定位为可运行任意不可信代码的多租户平台。

## 建议版本主线

### v0.2：建立可信证据

- 真实任务评测平台；
- P9 动态计划修订；
- 文档状态一致性检查。

**版本门**：真实任务报告可复现；计划修订可追溯、可拒绝、可选择性重跑；README、路线图和能力状态不再人工漂移。

### v0.3：降低成本并控制风险

- 增量验证；
- 风险驱动调度；
- 可复现执行与缓存。

**版本门**：与 v0.2 相同任务集相比，保持成功率与回归召回率，同时降低平均耗时或加权成本。

### v0.4：扩展吞吐与可操作性

- Git worktree 并行执行；
- 冲突协调节点；
- 运行轨迹可视化。

**版本门**：无冲突宽 DAG 获得可测量加速；冲突不会静默覆盖；操作者可从 UI 还原计划、执行和验收链路。

长期壁垒不是"会规划"，而是：**能够证明每一步为什么被执行、如何被验收、失败后如何恢复，并用真实评测证明这套机制比同样接了独立判卷的对照组更可靠。**

> 注（2026-11 修订）：原句写的是"比普通 Agent 更可靠"，**当前不可测**——普通 Agent 没有独立 oracle，它的"成功"是自述的，拿它当对照不成立。
> 可测的对照是"同一判据、不同反馈通道"（B0 臂 vs B2 臂），已经跑出来：B2 6/6 vs B0 0/6，`p=1.08e-3`。
> 完整论证见 [项目主张分析](analysis.md)。
